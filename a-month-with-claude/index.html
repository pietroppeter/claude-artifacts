Parte primaThe month in seven acts

Seven weeks of open source made with Claude: what happened, one moment from each act, and the parts of a way of working that grew along the way.

Since Opus 5.5 came out, Pietro has been writing open source with Claude, mostly from his phone. From 20 September to 7 November that made 289 pull requests and issues in 30 public repositories, his own and a few of others. That is too much to show, and this article does not try: no dashboard, no grid, no chart of every day. It picks.

It picks three things: the acts the month falls into, one moment from each act, and the parts of a way of working that each act added. The last are the point. They are what the second part puts together and names: Operetta.

This is also the first time tabelline is used on real data, by its own use it thread for 0.1 (see the roadmap): every table below is a tabelline table, and what it was missing is at the end.

Read top to bottom, the table tells how the way of working was built: first what any repo needs when it is made in throwaway cloud sessions (a setup script, pages built by CI, a line saying AI was used), then places to think in (explainers, artifacts), then ways to agree with Claude before building (specs, a backlog, proposals in their own PRs), and last the parts that only a library growing toward a reference needs (a coverage map, a book of ports, design posts, three threads per release).

How the work went

Behind the tables there is one loop, and it is the same in every act:

  1. An idea becomes a page. An explainer, often a claude-artifacts page made on the phone: the affinity propagation animation, the diagrams history, declarative dragging. Reading a page is how Pietro thinks with Claude.
  2. The page becomes a repo when the idea holds. zogyn and diagrammari started as artifacts; parloku as a notebook.
  3. The repo grows living documents: an explainer, the specs, a coverage map, a roadmap. They say how things are now, and are rebuilt on every push.
  4. The devlog keeps the story: dated posts, written while the decisions are fresh.
  5. Previews close the loop: a published page, read on the phone, with a link to the exact part that changed. Nothing reaches main without a "go".

What it leaves

Two questions, each with a part of its own:

  • Can the parts be picked, rather than all copied? nanuq used almost every one; cadero, a furniture plan, needed few; a talk needs different ones. The second part, Operetta, a first sketch, lists the parts as modules and says which to pick for what.
  • What are skills, and where do they go? They were tried once and set aside. The third part, Skills, from the beginning, starts from the simplest idea and ends with what Operetta could do with them.

What tabelline was missing

This part used tabelline as a user would, and sent what it found to the thread that builds 0.1:

Gaps found by this part
No TSV reader that leaves quotes alonereadCsv(sep = '\t') works, but a " in the middle of a title starts a quoted field and the quotes vanish (next to "live" reads next to live). Python needs quote_char=None, R quote = "".
No count or group-byExpected: tabelline is not a data frame library. A CountTable did the job; with nanuq it would be one line.
Small Markdown, no HTMLfmtMarkdown knows <br> but escapes any other tag (a <small> showed as text); an html() cell format would help. It also turned ~ and ^ into sub- and superscripts even with a space inside: fixed in 0.1 (#10).
Markdown in a group labelRow group labels come from the data as plain text; fmtMarkdown reaches cells, not groups, so act names stay plain.
No nanoplot for single valuesfmtBar covers it here. Great Tables and gt draw a single value as a bar with fmt_nanoplot(plot_type="bar"), planned for 0.4.
A colour from the pagefmtBar(color = "var(--blu, var(--pen))") works because the colour goes into a style attribute, so a page's CSS variables reach it. Worth saying so in the docs.

How this article is built

The page is a nimib notebook, docs/devlog/month_of_building.nim, built with the others by nim r -d:release docs/all.nim. Its data comes in three layers:

  • The raw data is docs/devlog/data/month-prs.tsv: one line per pull request or issue that Pietro opened between 20 September and 7 November, with its date, repository, number, state and title. It comes from GitHub's search API (author:pietroppeter, once with is:pr and once with is:issue). Search also returns private repositories, so each repository's visibility was checked and the private ones were dropped before the file was written.
  • The selection is docs/mese.nim, written by hand: the seven acts (name, dates, story, one moment, the repositories that belong to it) and the nineteen parts (what each is, and the pull request where it first appears). actOf puts every pull request in an act: by its repository when that belongs to one act, by its date otherwise.
  • The tables are tabelline: each tabella(rows, ...) call takes a seq of Nim objects or tuples, one field per column. rownameCol makes the stub, groupnameCol the row groups, and fmtMarkdown turns **bold**, links and <br> in the cells into HTML. The bars are fmtBar, coloured with the page's own CSS variables. tabella is a macro: it makes the table with initTabella, then reads its indented body one line at a time, so that tabHeader "Title" becomes t = t.tabHeader("Title"). The rest is plain Nim: the verbs are procs.

Nothing is fetched while the page is built: the TSV is in the repository, so the page builds offline and the same way every time.

Parte secondaOperetta, a first sketch

A name for the way of working that grew in the month: parts that a project picks by what it is and how far along it is, and adds to as it grows.

Operetta is a way to make an open source library with an AI agent. It is not a tool and not a template: it is a list of parts (a setup script, an explainer, specs, a devlog, a coverage map, skills, ...), and a project uses the ones it needs. Each part is small, and each one was already made once, in a project of the last month (the first part says where). Until now they were copied by hand from one repo to the next, and every copy drifted a little; with a name they become something to pick from, and to improve in one place.

The name is Operetta. It came with Opus 5.5, the model the month was built with: a small opus. And an operetta is a light, modular show, with songs between spoken parts; a company can stage a short one with a few numbers or a long one with all of them.

The idea in one sentence

The explainer is where the thinking happens; every other part keeps it true.

A page that explains the idea, made with Claude and read on the phone, is how a project moves: first as a claude-artifacts sketch, then as the living explainer of a repo. Specs, the devlog, coverage maps, books and benchmarks are there so that the page, the code and Claude's next session agree.

Each group has an Italian name from the theatre, so the five are easy to tell apart, and a plain one, so they are easy to understand.

The prompter, il suggeritore, sits in a box under the stage and whispers the lines to the singers when they need them, and only then. That is what a skill does for an agent, which is why the fifth group has his name and why it has only one part today: it is the next one to grow, and the subject of the third part.

A project does not pick once. It starts small and adds a group when it reaches the stage that needs it. Each stage has a sign that says it is time:

A part has variations

Copying showed that a part is not one template. Each has a few ways to be done, and a project picks one:

  • Specs. nanuq writes the proposal and the implementation in separate pull requests; tabelline and parloku in one. parloku's scenarios are drags that run and animate on the specs page; the talk has a schema of its own, with an abstract, an outline and its islands.
  • Book. nanuq's book is a repository of its own, with a CI that rebuilds only the chapters that changed; tabelline's book will live in the main repository, until its CI grows heavy.
  • Look. Every project has its own theme; tabelline has two, and its devlog posts can have one each.
  • Explainers. Nim only, or Nim, Python and R in tabs, checked to agree.

So Operetta describes each part with its variations and says when to pick which, rather than shipping one way of doing it.

Still open

  • Where it lives. A repository of its own, later, holding the parts as short documents, a small template for each, and one skill per part (add a devlog post, start a coverage map, publish a preview with deep links). Installed as a plugin, the skills would be how a project picks parts: the third part explains why that fits.
  • Keeping copies in step. Today a part improved in one repo stays there. With skills, the next session in any project that picked it gets the improved version.
  • The garden. A place for ideas and notes that are neither backlog nor posts; how it works is not decided yet, so it is not a part yet.
  • How heavy it gets. Every part costs CI time and attention. The rule so far: a part comes in when a stage's sign shows, not before.

This is a sketch. The next projects will move parts between groups, split some and drop others, and that is how it should go: complicare è facile, semplificare è difficile.

Parte terzaSkills, from the beginning

What an agent skill is, where skills live in an open source project, who does them well, how they work from the phone, and how to tell whether one helps.

Skills are the fifth group of Operetta, the suggeritore, and the one with the least in it. This part starts from nothing and goes step by step.

A skill is a folder

A skill is a folder with a file called SKILL.md in it. The file starts with two fields, a name and a description, and goes on with instructions in plain Markdown. The folder can also hold scripts to run and longer references to read. That is all: no code to install, no server.

Here is the top of a skill that is in tabelline's repository, put there by OpenSpec:

---
name: openspec-propose
description: Propose a new OpenSpec change with all artifacts generated in one step. Use when the user wants to quickly describe what they want to build and get a complete proposal with design, specs, and tasks ready for implementation. Also use when the user says "openspec propose" or "opsx propose".
allowed-tools: Bash(openspec:*)
license: MIT
compatibility: Requires openspec CLI.
metadata:
  author: openspec
  version: "1.0"
  generatedBy: "1.16.0"
---
...

What makes skills work is when each part is read. The agent sees only the name and the description of every skill it has, a line or two each. It reads the rest of SKILL.md only when a task matches the description, and the scripts and references only if the instructions send it there. A project can carry many skills and pay for the ones in use. The Agent Skills format is an open standard: Claude Code, Codex, Cursor and others read the same folders.

That is why OpenSpec can feel like it is not there. Typing /opsx:propose runs the command; asking "let's propose a change for summary rows" makes the agent load the skill on its own. Either way 11 to 23 KB of instructions arrive (3,000 to 6,000 tokens), only for that task, and the work just goes the OpenSpec way. A skill that works well is mostly invisible.

Where skills live

For an open source library there are two audiences, and they want different skills in different places:

  • People who work on the library (and their agents): how to build it, test it, write a spec, make a release. These skills belong in the repository, next to AGENTS.md, and change with it.
  • People who work with the library: how to use its API today. These belong with the documentation, versioned with the releases, so that a user gets the skill that matches the version they have.

Then there is where a skill is put on a computer, or an account:

Matt Pocock's choice is a useful warning for Operetta. He keeps skills small because frameworks like Spec-Kit or BMAD, in his words, take away your control. Operetta has to stay a set of parts to pick, each one small, and not become one of those.

From the phone

Pietro works with Claude Code mostly from the phone, in cloud sessions: each one starts on a fresh clone of the repository. That decides where skills should go:

  • Skills in the repository always come along. This article was written in such a session, and tabelline's six OpenSpec skills were there without anything installed.
  • Skills uploaded to the claude.ai account are there in the Claude apps, and Claude Code syncs them too; in the session that wrote it, one of Pietro's own skills was present next to the repository's.
  • Plugins can also be listed in the repository's .claude/settings.json. How that behaves in a session started from the phone was not tested here, so for cloud sessions the repository's own .claude/skills/ is the dependable place.

So: skills for working on a project go in its repository; personal skills, for any project, go in the account.

Does a skill help?

A skill can fail three ways: it does not fire, it fires and does not help, or it was true once and is not any more. Each needs its own test:

Two studies from this year say what to expect:

  • SkillsBench (February 2026) ran agents on about 85 tasks in 11 domains with and without skills. Skills written by people raised the pass rate by 16 points on average, from 4.5 in software engineering to 52 in healthcare, and made 16 tasks worse. Skills the models wrote for themselves gave nothing. Focused skills, with two or three parts, beat complete documentation.
  • Vercel (January 2026) tested agents writing Next.js 16 code. An 8 KB index of the docs in AGENTS.md passed every test; skills passed at most 79%, and when the agent did not call the skill it did no better than with no docs at all (53%).

The lesson for a small library: what every session needs goes in AGENTS.md, which is always read; procedures that only some tasks need go in skills; and a skill that is not tested for firing may as well not be there. The numbers come from the papers' summaries, read through search: both pages were blocked from the sandbox.

For tabelline and Operetta

Three small steps, in order, none of them for today:

  1. A skill for tabelline's users, built by the docs: skill.md and llms.txt written from the specs while the pages are built, the way Great Docs does it for Great Tables, and served from the site. Every requirement already has an example that runs, so the skill would be checked on every push for free. Models trained before November 2026 have never seen tabelline, so this is where a skill helps most.
  2. A small benchmark for it: five tasks (a table with a header and a spanner, formatted numbers, a styled column, a nimib page, a Great Tables snippet ported), each with and without the skill, graded by building the result.
  3. One skill per Operetta part, kept in Operetta's repository when it has one and installed as a plugin, or copied into a project's .claude/skills/ for cloud sessions: add a devlog post, start a coverage map, publish a preview with deep links. Picking a part would be adding its skill.

The first two are in tabelline's backlog.
