Puščica: Apache Arrow, told with Kosovel

Apache Arrow is a promise about memory: this is exactly how a table of data sits in RAM, down to the byte. Keep the promise, and a table made by one program can be read by another, in another language, without converting or copying a thing. In ten years that promise has spread to most of the modern data stack.

To see what it means, byte by byte, we need a table. Ours is made of poems by Srečko Kosovel (1904–1926), the poet of the Karst, who died at 22 and left behind hundreds of poems, from gentle landscapes to the wild, typographic konsi. Slovenian is a good test: č, š and ž each take two bytes, which is exactly where an Arrow string column gets interesting.

Puščica is Slovenian for a small arrow.

The data: 509 texts, in an Arrow file

Kosovel's poems are on the Slovenian Wikisource, Wikivir, all marked javna last (public domain). A script (data/make_dataset.py) went through the monthly Wikisource dump, kept every page by Kosovel, and wrote one table, one row per text, three ways: Parquet (to store), an Arrow IPC stream (to load), and JSON (for your browser).

Rows, or columns

A table can sit in memory in two ways. Row by row, each poem's title, kind and word count next to each other, the way a CSV file or a list of objects does it. Or column by column: all the titles, then all the kinds, then all the word counts.

Analytics loves columns. "How many words did Kosovel write?" reads one column and nothing else, in one straight run through memory, which is what CPU caches and SIMD instructions are built for. Compression likes columns too: a column of kinds repeats three values.

Every data system knew this, and each had its own columnar layout: pandas had NumPy arrays and Python objects, Spark had its own, every database its own. Moving a table from one to the next meant converting it, value by value, and a lot of time in data pipelines went to exactly that. Arrow's idea (2016) was to agree, once, on one layout that everyone could use as their own memory, so that handing a table over is handing over a pointer.

A column of strings, byte by byte

Take the first stanza of Bori (pines), with the empty line after it, as a column of four strings. In Arrow (the spec) a utf8 column is three buffers:

  1. a validity bitmap: one bit per value, 1 if the value is there, 0 if it is null;
  2. offsets: length + 1 integers (int32), where each value starts and ends;
  3. data: all the bytes of all the strings, end to end, with nothing in between.

The empty line is a null here: no value at all (Arrow keeps "missing" apart from "empty string"). This is lib/layout.nim, the same code that draws the explorer below:

Each value is the slice of the data buffer between two neighbouring offsets. The null has two equal offsets (it takes no bytes) and a 0 in the bitmap. Reading row i is two lookups, no scanning: Arrow is built for random access too.

Characters are not bytes

The offsets count bytes, and Arrow strings are UTF-8. The ASCII letters take one byte each, but č, š, ž take two (c4 8d, c5 a1, c5 be), and Kons. 5's ∞ takes three:

Over the whole corpus, Kosovel's 238026 characters take 245684 bytes. The most common characters outside ASCII: č 3083, š 1917, ž 1132, — 319, Č 137, ó 112. So a "string length" in Arrow is a length in bytes, and an Arrow-speaking library that counts letters (Polars' len_chars, pyarrow's utf8_length) has to walk the bytes.

The idea

Everything in an Arrow column is a flat buffer of fixed-width things (bits, int32s, bytes), and buffers are aligned to 8 bytes and padded to 64 in files, so they can be memory-mapped and fed straight to SIMD. No pointers inside: that is what makes the same bytes valid in C++, Rust, Java, JavaScript, Python, R... and Nim.

The layout explorer

Pick a poem, tap a value, and see the bytes it is made of, in four encodings of the same column. Lines makes a column of the poem's lines (blank lines are nulls); Words a column of its words. The two sliders take a slice: in Arrow a slice is the same buffers with a different offset and length, so nothing is copied, and what is outside it is greyed out.

Four ways to write the same strings

utf8 is the classic, shown above. Its cousin large_utf8 (U) is the same with int64 offsets, for columns over 2 GB.

Dictionary encoding stores each distinct value once, in a little utf8 column (the dictionary), and the column itself becomes integers (the indices). Great when values repeat, like words in poems, or the kind column. pandas calls this a categorical, Polars a Categorical or Enum, R a factor. Over all of Kosovel:

Saving bytes is half the story. The other half is that the indices are small integers, so "group by word" or "how often" is integer work on 41227 int32s, not string comparisons. The most frequent words in the dictionary are the little ones: v 1313, in 1300, je 1248, se 803, da 482, na 447, ne 425, so 348, bi 314, ki 298, sem 283, ti 266. The longest is ljudskoprosvetnega.

Run-end encoding (added in 2023) stores runs: each run's value once, and where the run ends. It shines when the same value repeats in a row, like a column with the title of the poem next to every word:

Kosovel loved repetition (bori, bori, bori, bori!), but a poem's words rarely repeat in a row: in the explorer, Bori in words makes 80 runs out of 87 words, and run-end costs more than plain utf8, while the title column above shrinks 67 times. Encodings fit data, not poets. And to find a row, a run-end reader has to binary-search the run ends: random access costs log(runs) instead of one lookup.

String views (utf8_view, also 2023) are the newest, and come from databases: they were introduced by the Umbra system at TU Munich ("German strings") and adopted by DuckDB, Velox and Polars. Each value gets a fixed 16-byte view: 4 bytes of length, then either the whole string, if it fits in 12 bytes, or its first 4 bytes, a buffer number and an offset. Short strings never leave the view, comparisons can often stop at the prefix, and the data buffers can be shared and appended to in any order. In Kosovel, 99% of the words fit in their view, but only 13% of the lines.

Arrow has more layouts than strings, all built from the same pieces: fixed-width numbers (a values buffer and a bitmap), booleans (one bit each), lists (offsets into a child column), list views, structs (one child per field, so a whole table is a struct column), unions, maps, decimals, dates, times, timestamps with time zones, durations, intervals, and extension types (a UUID, a tensor, a geometry) that are a storage type plus a name in the metadata.

The Arrow family

The columnar format is the heart. Around it the project grew a family of specifications, each one answering "and how do I move it there?":

  • The C Data Interface (spec, 2020): two C structs, ArrowSchema and ArrowArray, that describe a column and point at its buffers, plus ArrowArrayStream for a stream of batches. No library needed: anyone who can write a C struct can hand Arrow data to anyone else in the same process. Python wraps them in PyCapsules (__arrow_c_array__, __arrow_c_stream__), so pyarrow, Polars, DuckDB, pandas and friends swap tables without knowing about each other. There is a C Device variant for GPU memory.
  • IPC: the same buffers, written to a file or a socket, with a little FlatBuffers metadata in front. Reading it back is mostly a memory map, no parsing. The file format (with a footer, for random access to batches) is also known as Feather (v2); the stream format is what this page loaded the poems from.
  • Flight: Arrow over the network, on gRPC: streams of record batches, in parallel, between services. Flight SQL puts a SQL database behind it.
  • ADBC (Arrow Database Connectivity): a database API like JDBC or ODBC, but results come back as Arrow. Drivers for PostgreSQL, SQLite, Snowflake, BigQuery, Flight SQL, DuckDB...
  • Implementations: official libraries in C (nanoarrow, GLib), C++, C#, Go, Java, JavaScript, Julia, MATLAB, Python (pyarrow), R, Ruby and Rust (arrow-rs), with readers, writers and compute functions (C++ even has a query engine, Acero).

And Parquet?

Apache Parquet is Arrow's sibling on disk, and they were born together (some of Parquet's founders were in the room when Arrow was designed). Parquet is for storing: columns split into pages, encoded (dictionary, run-length, delta, bit packing) and compressed, with statistics for skipping. Arrow is for working: uncompressed (or lightly), fixed layouts, random access, ready for the CPU. The typical life of data is Parquet on disk, Arrow in memory. Most Parquet implementations now live inside the Arrow repositories (C++, Rust, Go). For Kosovel:

The people

Arrow is an Apache Software Foundation project, so it is run by its community, not by a company. Contributors who keep showing up become committers (they can merge); some committers join the PMC, the Project Management Committee that votes on releases and new members; one PMC member is the project's VP, its contact with the foundation. Arrow has no roadmap: decisions are by consensus on the mailing list, and format changes need a vote and two implementations that pass the integration tests.

A short history:

  • 2016: the project starts (first commit 5 February), co-created by people from many data projects, among them Wes McKinney (pandas) and Jacques Nadeau (Dremio), with founders of Parquet such as Julien Le Dem. 0.1.0 comes out in October, with C++ and Java.
  • 2020: version 1.0.0, and formal stability promises. The C Data Interface is added. Since then, the format has had one breaking change (unions lost their validity bitmap, in 2020) and nothing since: new types are additions.
  • 2023: string views, list views, run-end encoding.
  • 2024: DataFusion graduates to its own top-level project.
  • 2025: Voltron Data, which had employed many core developers, winds down; the community moves its benchmarking and nightly infrastructure to Arrow's own accounts. The first Arrow Summit is held in Paris in October.
  • 2026: ten years old in February. Version 26.0.1 in November; nanoarrow 0.9, ADBC 25, arrow-rs 60, arrow-go 18.9, arrow-java 20 along the way.

The committer list has 62 PMC members (with the VP, Antoine Pitrou) and 59 more committers.

A Column holds its buffers as Nim seqs. exportTo fills two structs owned by the caller with pointers into them, and keeps the column alive (a GC_ref) until the consumer calls release. Nothing is copied. To prove it works with real consumers, poc/libkosovel.nim builds a shared library around it, and a 30-line Python script loads it with ctypes and hands the record batch to pyarrow, Polars and DuckDB. This ran when the page was built, on the words of Bori:

## and reads theirs. Build: nim c --app:lib -d:release -o:libkosovel.so libkosovel.nim

proc kosovel_set_words(text: cstring) {.exportc, dynlib, cdecl.} =
  ## Give the library its words (one per line).
  words = ($text).splitLines

proc kosovel_export_batch(s: ptr ArrowSchema; a: ptr ArrowArray) {.exportc, dynlib, cdecl.} =
  ## A record batch with four columns of the same words, in four encodings.
  var lens: seq[int32]
  for w in words: lens.add int32(w.runeLen)
  structColumn("", [utf8Column("word", words), dictColumn("word_dict", words),
                    stringViewColumn("word_view", words), runEndColumn("word_runs", words),
                    int32Column("letters", lens)]).exportTo(s, a)

  ## Read a utf8 column made by someone else, in place, and count č, š, ž (any case).
  for w in utf8Values(s, a):
    for r in w.runes:
      if r.toLower in [Rune(0x10D), Rune(0x161), Rune(0x17E)]: inc result

Four things to notice. pyarrow's validate(full=True) accepted every buffer Nim made, including the views and the run-end column. Polars refused the run-end column ("+r" is still not supported): every consumer implements a subset of the types, and the newest ones arrive last. DuckDB took it. nanoarrow, compiled in

For everything beyond the C Data Interface (reading IPC files, validating arrays, streams) there is no need for a system library either. nanoarrow ships as a few C files, and Nim can compile C files right into a program with {.compile.}. lib/nanoarrow.nim does that, declares the handful of functions it needs, and gives an iterator over the record batches of an IPC stream. That is how this page read the poems at the top: nanoarrow parsed the file, and handed each batch back as the same ArrowArray struct cdata.nim knows, so utf8Values read the strings straight out of nanoarrow's buffers.

Back to Kosovel

Srečko Kosovel was born in Sežana in 1904 and grew up in Tomaj, on the Karst, and studied in Ljubljana, where he edited student magazines, organized readings, and wrote at a furious pace. He died of meningitis in 1926, at 22. Little was published in his lifetime: the first book of his poems came out in 1927, the constructivist Integrali '26 only in 1967, and with them he became one of the great European avant-garde poets.

He moves from impressionist Karst landscapes (the pines, the bora wind, the juniper) to expressionist visions of a dying Europe (Ekstaza smrti) and to the konsi: poems as constructions of words, numbers, signs and typography, close to the constructivists of Moscow and the artists in Trieste around Avgust Černigoj. He also wrote for children, which is why the looks of this page come from Slovenian picture books: Naša bela mačica (our white kitten), the bear cubs, the sparrow and the dormouse are all in the explorer's list.

Glossary, for the next conversation with an Arrow committer

  • Array / column: one typed column, a few buffers. Chunked array: a column made of several arrays. Record batch: equal-length arrays with a schema (a struct column). Table: a schema and chunked arrays.
  • Schema / field: names, types, nullability, key-value metadata.
  • Validity bitmap: one bit per value, LSB first; absent when nothing is null.
  • Offsets: where variable-length values start; int32 (utf8, list) or int64 (large_*).
  • Views: 16 bytes per value: length, prefix or inline bytes, buffer index, offset.
  • Dictionary, run-end encoding: repeated values stored once, as indices or as runs.
  • Zero-copy: handing over pointers to the same buffers, never converting.
  • Slice: same buffers, a different offset and length.
  • C Data Interface / C Stream / C Device: the structs for passing arrays, streams, and GPU arrays.
  • IPC / Feather: the in-memory layout, framed for files and sockets.
  • Flight / Flight SQL / ADBC: over the network, and the database API.
  • Extension type: a storage type plus a name (arrow.uuid, arrow.fixed_shape_tensor, GeoArrow).
  • Canonical extension: an extension type the project itself standardised.
  • PMC, committer, VP: the Apache way of running a project.

  for k in 0..3: b.add (v shr (8 * k)) and 0xff

proc validity(valid: openArray[bool]): Buf =
  ## One bit per value, least significant bit first. Absent when there are no nulls.
  result = Buf(name: "validity", width: 1)
  var nulls = 0
  for v in valid:
    if not v: inc nulls
  if nulls == 0: return
  result.bytes = newSeq[int]((valid.len + 7) div 8)
  result.owner = newSeq[int](result.bytes.len)
  for i, v in valid:
    if v: result.bytes[i div 8] = result.bytes[i div 8] or (1 shl (i mod 8))
  for i in 0 ..< result.bytes.len: result.owner[i] = -1

proc utf8Layout*(values: openArray[string]; valid: openArray[bool] = []): Layout =
  ## Offsets (length + 1 int32) into a single buffer holding every string's bytes, end to end.
  result = Layout(encoding: encUtf8, length: values.len, format: "u")
  var ok = newSeq[bool](values.len)
  for i in 0 ..< values.len: ok[i] = valid.len == 0 or valid[i]
  for v in ok:
    if not v: inc result.nullCount
  var offs = Buf(name: "offsets", width: 4)
  var data = Buf(name: "data", width: 1, text: true)
  offs.bytes.le32 0
  for k in 0..3: offs.owner.add -1
  for i, v in values:
    if ok[i]:
      for c in v:
        data.bytes.add ord(c)
        data.owner.add i
    offs.bytes.le32 data.bytes.len
    for k in 0..3: offs.owner.add i         # offset i+1 is where value i ends
  result.buffers = @[validity(ok), offs, data]
  result.note = "value i is data[offsets[i] ..< offsets[i+1]]"

proc viewLayout*(values: openArray[string]; valid: openArray[bool] = []): Layout =
  ## One 16-byte view per value: length (4 bytes), then either the string itself (up to 12
  ## bytes, padded with zeros) or a 4-byte prefix, a buffer index and an offset.
  result = Layout(encoding: encView, length: values.len, format: "vu")
  var ok = newSeq[bool](values.len)
  for i in 0 ..< values.len: ok[i] = valid.len == 0 or valid[i]
  for v in ok:
    if not v: inc result.nullCount
  var views = Buf(name: "views", width: 16)
  var data = Buf(name: "data 0", width: 1, text: true)
  var inline = 0
  for i, v0 in values:
    let v = if ok[i]: v0 else: ""
    views.bytes.le32 v.len
    if v.len <= 12:
      inc inline
      for k in 0 ..< 12: views.bytes.add(if k < v.len: ord(v[k]) else: 0)
    else:
      for k in 0 ..< 4: views.bytes.add ord(v[k])
      views.bytes.le32 0
      views.bytes.le32 data.bytes.len
      for c in v:
        data.bytes.add ord(c)
        data.owner.add i
    for k in 0 ..< 16: views.owner.add i
  var sizes = Buf(name: "sizes", width: 8)
  sizes.bytes.le64 data.bytes.len
  for k in 0 ..< 8: sizes.owner.add -1
  result.buffers = @[validity(ok), views, data, sizes]
  result.note = $inline & " of " & $values.len & " values fit inside their view (12 bytes or less)"

proc dictLayout*(values: openArray[string]): Layout =
  ## Every distinct value once, in a utf8 dictionary; the column itself is int32 indices.
  var dict: seq[string]
  var seen = initTable[string, int]()
  var idx = Buf(name: "indices", width: 4)
  for i, v in values:
    let k = seen.mgetOrPut(v, dict.len)
    if k == dict.len: dict.add v
    idx.bytes.le32 k
    for j in 0..3: idx.owner.add i
    result.childIndex.add k
  result = Layout(encoding: encDict, length: values.len, format: "i",
                  buffers: @[Buf(name: "validity", width: 1), idx],
                  children: @[utf8Layout(dict)], childNames: @["dictionary"],
                  childIndex: result.childIndex)
  result.note = $values.len & " values, " & $dict.len & " distinct"

proc runEndLayout*(values: openArray[string]): Layout =
  ## Runs of equal neighbours: where each run ends (int32), and each run's value (utf8).
  var ends = Buf(name: "run_ends", width: 4)
  var vals: seq[string]
  var runOf: seq[int]
  for i, v in values:
    if vals.len > 0 and vals[^1] == v:
      ends.bytes.setLen ends.bytes.len - 4
      ends.owner.setLen ends.owner.len - 4
    else:
      vals.add v
    ends.bytes.le32 i + 1
    for j in 0..3: ends.owner.add vals.len - 1
    runOf.add vals.len - 1
  result = Layout(childIndex: runOf, encoding: encRunEnd, length: values.len, format: "+r",
                  children: @[Layout(encoding: encUtf8, length: vals.len, format: "i", buffers: @[Buf(name: "validity", width: 1), ends]),
                              utf8Layout(vals)],
                  childNames: @["run_ends", "values"])
  result.note = $values.len & " values in " & $vals.len & " runs"

proc layout*(e: Encoding; values: openArray[string]; valid: openArray[bool] = []): Layout =
  case e
  of encUtf8: utf8Layout(values, valid)
  of encView: viewLayout(values, valid)
  of encDict: dictLayout(values)
  of encRunEnd: runEndLayout(values)

  for b in l.buffers: result += b.bytes.len
  for c in l.children: result += c.totalBytes

def field(tpl, name):
    m = re.search(r"\|\s*" + name + r"\s*=\s*([^\n]*)", tpl)
    if not m:
        return ""
    v, depth = m.group(1), 0
    for i, c in enumerate(v):       # stop at a "|" outside [[...]]: the next field
        depth += (c == "[") - (c == "]")
        if c == "|" and depth == 0:
            return v[:i].strip()
    return v.strip().removesuffix("}}")

def clean(s):

## The Arrow family

The columnar format is the heart. Around it the project grew a family of specifications,
each one answering "and how do I move it *there*?":

proc compileWidgets*(src, scratch: string): string =
  ## `nim js` the widgets at build time; the page inlines the result (artifacts allow no other host).
  createDir scratch
  let outp = scratch / "widgets.js"
  let (o, code) = execCmdEx("nim js -d:danger --hints:off --warnings:off -o:" & quoteShell(outp) & " " & quoteShell(src))
  doAssert code == 0, o
  readFile(outp)

## Glossary, for the next conversation with an Arrow committer

- **Array / column**: one typed column, a few buffers. **Chunked array**: a column made of
  several arrays. **Record batch**: equal-length arrays with a schema (a struct column).
  **Table**: a schema and chunked arrays.
- **Schema / field**: names, types, nullability, key-value metadata.
- **Validity bitmap**: one bit per value, LSB first; absent when nothing is null.
- **Offsets**: where variable-length values start; int32 (`utf8`, `list`) or int64 (`large_*`).
- **Views**: 16 bytes per value: length, prefix or inline bytes, buffer index, offset.
- **Dictionary, run-end encoding**: repeated values stored once, as indices or as runs.
- **Zero-copy**: handing over pointers to the same buffers, never converting.
- **Slice**: same buffers, a different offset and length.
- **C Data Interface / C Stream / C Device**: the structs for passing arrays, streams, and GPU arrays.
- **IPC / Feather**: the in-memory layout, framed for files and sockets.
- **Flight / Flight SQL / ADBC**: over the network, and the database API.
- **Extension type**: a storage type plus a name (`arrow.uuid`, `arrow.fixed_shape_tensor`, GeoArrow).
- **Canonical extension**: an extension type the project itself standardised.
- **PMC, committer, VP**: the Apache way of running a project.
"""
