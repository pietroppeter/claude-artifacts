Two plugs for one Nim library

diagrammari has a Nim procedure that turns Mermaid text into SVG. Python can call it through two plugs: A a C ABI loaded with ctypes, or B a nimpy module. I built both from the same Nim code, with nimlang as the compiler, and measured them side by side.

In short

  • Both plugs give byte-identical SVG at the same speed, about 0.8 ms a diagram. The call itself costs 0.1 µs or less.
  • Both are one file per platform for every Python from 3.9 to 3.14, with nothing to install at run time.
  • They differ on who checks the arguments, how errors and Python objects cross, the GIL, and who else can load the library.
  • nimlang built all five platform wheels on one Linux machine, 1.2 MB each.
  • The comparison found a thread bug both plugs shared. It is fixed.

1 The procedure

Everything starts from one Nim procedure. It takes a JSON request with the Mermaid text, a personal layer and Pele's options, and answers in JSON: the SVG and the ids a layer can use, or Pele's error.

# capi.nim: the Nim side, before any plug
proc draw(req: JsonNode): JsonNode
  ## req:    {"source": "<Mermaid text>", "layer": {...}, "options": {...}}
  ## answer: {"ok": true, "svg": "<svg ...>", "type": "flowchart",
  ##          "ids": {"nodes": [...], "edges": [...]}}
  ##   or:   {"ok": false, "code": "syntax", "message": "...",
  ##          "line": 2, "column": 9, "snippet": "..."}
>>> mari.draw("flowchart LR\n  a --> b")
{"ok": true, "svg": "<svg xmlns=\"http://www.w3.org/2000/svg\" ...", "type": "flowchart",
 "ids": {"nodes": ["a", "b"], "edges": ["L_a_b_0"]}}
>>> mari_draw('{"source": "flowchart LR\n  a --> ["}')
{"ok":false,"code":"syntax","message":"Parse error on line 2:\n  a --> [\n--------^\nExpecting 'NODE_STRING', got 'SQS'",
 "line":2,"column":9,"snippet":"  a --> [\n--------^"}

The job is to call this procedure from Python. A plug is the code on both sides of that border.

2 Two plugs

Each column reads in the order a call travels: what the Python user writes, then the Python side of the plug, then the Nim side.

A C ABI + ctypes

Nim exports C functions that take and return C strings. Python loads the library with ctypes and sends the request as one JSON string. The library allocates the answer, so the library frees it.

import mari
mari.draw("flowchart LR\n  a --> b")["svg"]    # -> str
# mari/__init__.py: the Python half of plug A
def draw(source: str, layer: dict | None = None, **options) -> dict:
    req = json.dumps({"source": source, "layer": layer or {}, "options": options}).encode()
    p = lib.mari_draw(req)
    try:
        answer = json.loads(ctypes.string_at(p).decode())
    finally:
        lib.mari_free(p)                       # the library made it, the library frees it
    if not answer.get("ok"):
        raise DiagramError(answer)             # .code .line .column .snippet
    return answer

lib = ctypes.CDLL(str(_here / _libname))       # loaded once, at import
lib.mari_draw.argtypes = [ctypes.c_char_p]
lib.mari_draw.restype = ctypes.c_void_p        # a pointer: c_char_p would copy and lose it
lib.mari_free.argtypes = [ctypes.c_void_p]
# capi.nim: the Nim half of plug A
proc mari_draw(request: cstring): cstring {.exportc, dynlib, cdecl.} =
  var answer: string
  try:
    answer = $draw(parseJson($request))
  except CatchableError as e:
    answer = $(%*{"ok": false, "code": "error", "message": e.msg})
  result = cast[cstring](allocShared0(answer.len + 1))
  copyMem(result, answer.cstring, answer.len)

proc mari_free(p: cstring) {.exportc, dynlib, cdecl.} = deallocShared(p)

B nimpy

nimpy writes the Python module. Nim strings become Python strings, a Nim exception becomes a Python exception, and the memory is Nim's. It finds libpython when the module is loaded, so one build serves every Python 3. There is no Python side to write.

import marinp
marinp.svg("flowchart LR\n  a --> b")              # -> str
# marinp.nim: all of plug B
include capi
import nimpy

proc svg(source: string, layer: string = "{}"): string {.exportpy.} =
  let a = draw(%*{"source": source, "layer": parseJson(layer), "options": {}})
  if not a["ok"].getBool:
    raise newException(ValueError, a["code"].getStr & ": " & a["message"].getStr)
  a["svg"].getStr

The Python API in the package is plug A's: mari.draw(source, layer=None, **options) -> dict with the keys above, and mari.Diagram(source, layer=None) with .svg, .save(path) and .ids(). Plug B here is a test module, marinp, with svg(source, layer="{}") -> str.

Caution: a mistake in the plug

With plug A, a mistake in the ctypes wrapper crashes Python. The user can't catch it, and a notebook kernel dies. With plug B the same kind of mistake is a Python exception. Users never touch ctypes, so the risk sits in our 20 lines, and the tests cover it.

$ python -c "import mari; mari._lib.mari_free(12345)"
SIGSEGV: Illegal storage access. (Attempt to read from nil?)
Segmentation fault       # exit 139
$ python -c "import marinp; marinp.svg(42)"
TypeError: Can't convert python obj of type
'int' to string

4 Nim to QuickJS

Behind the procedure is a second border, the same for both plugs. Pele is JavaScript, and it runs in QuickJS, compiled into the library. QuickJS passes values as JSValue, whose shape depends on the platform and the build flags: a pointer, a NaN-boxed 64-bit integer, or a 16-byte struct. Many of its helpers are macros. A 52-line C shim keeps JSValue on the C side and gives Nim four plain functions with pointers and strings.

Drawn by the library on test: Python called mari, which ran Pele in QuickJS.

# qjs.nim: what Nim sees of QuickJS
{.compile(qjsDir & "/quickjs.c", qjsFlags).}   # and libregexp.c, libunicode.c, dtoa.c
{.compile(here & "/mari_qjs.c", qjsFlags).}
proc mari_js_new(code: cstring, len: csize_t, err: ptr cstring): pointer {.importc, cdecl.}
proc mari_js_call(h: pointer, fn, arg: cstring, len: csize_t, ok: ptr cint): cstring {.importc, cdecl.}
proc mari_js_free_str(s: cstring) {.importc, cdecl.}
/* mari_qjs.c: QuickJS's JSValue stays on the C side */
void *mari_js_new(const char *code, size_t len, char **err);   /* runtime + context, script evaluated */
char *mari_js_call(void *h, const char *fn, const char *arg, size_t len, int *ok);
void  mari_js_free_str(char *s);
void  mari_js_close(void *h);
// qjs.nim: appended to Pele's bundle, the one function Nim calls
globalThis.__mari = function (line) {
  const q = JSON.parse(line);
  const r = pele.render(q.source, q.options || {});
  const a = { ok: true, svg: r.svg, type: r.type, ends: {} };
  if (r.type === 'flowchart') for (const e of pele.parse(q.source).edges) a.ends[e.id] = [e.start, e.end];
  return JSON.stringify(a);           // errors: {ok: false, code, message, line, column, snippet}
};

5 Drawing from threads

Drawing 400 diagrams from a pool of 8 Python threads failed on both plugs. The error came from QuickJS.

$ python threads.py ctypes    # 8 threads, 400 diagrams
mari.DiagramError: js: Maximum call stack size exceeded
$ python threads.py nimpy
nimpy.ValueError: Unexpected error encountered:
  js: Maximum call stack size exceeded
$ python threads.py ctypes
ctypes 8 threads: 400 of 400 right, 280 ms
$ python threads.py nimpy
nimpy 8 threads: 400 of 400 right, 202 ms

QuickJS checks for stack overflow by comparing the current stack with the one where the runtime was made. A call from another thread has a different stack, so every call there looked like an overflow. Behind it was a second problem: plug A lets go of the GIL during the call, so two threads could have entered the same runtime at once. The fix has two parts, outside in. A Nim lock lets one call into the runtime at a time. Inside the lock, the shim tells QuickJS which stack the caller is on. The JavaScript stack limit went from 8 MB to 1 MB, because Python threads can have smaller stacks than the main thread. A 500-edge flowchart and 30 nested subgraphs still draw, in 107 ms and 3 ms.

# qjs.nim: one QuickJS runtime for the process, one call at a time
var
  engine: pointer
  engineLock: Lock
initLock engineLock

proc askQjs*(bundle: string, req: JsonNode): JsonNode =
  ...
  withLock engineLock:
    startEngine(bundle)
    let r = mari_js_call(engine, "__mari", s.cstring, s.len.csize_t, addr ok)
    ...
/* mari_qjs.c: inside the lock, tell QuickJS which stack this thread is on */
char *mari_js_call(void *h, const char *fn, const char *arg, size_t len, int *ok) {
  MariJs *m = h; JSContext *ctx = m->ctx;
  JS_UpdateStackTop(m->rt);
  ...

The threads do not draw in parallel on either plug: there is one QuickJS runtime and one lock. Plug A lets other Python threads run during a draw; plug B does not.

6 Wheels with nimlang

nimlang ships the Nim compiler in a wheel and compiles C with zig cc from the ziglang wheel. As a build requirement, it lets uv build work with no Nim and no C compiler installed. Its hatch hook is made for nimpy modules, but it builds plug A's library unchanged. The file just has to be a Nim module that includes capi.nim, and the loader finds native.so, .pyd or .dylib.

[build-system]
requires = ["hatchling>=1.24", "nimlang>=0.0.3"]
build-backend = "hatchling.build"

[tool.hatch.build.hooks.nimlang]
extensions = ["src/mari/native.nim"]   # a C ABI library: ctypes loads it, nimpy is not needed
# src/mari/native.nim (a Nim module name: no leading underscore)
include "../../nim/capi"

Caution: paths when cross-compiling for Windows

In Nim, / and parentDir use the target's separator. Cross-compiling for Windows from Linux turned the compile-time path to QuickJS's C files into \home\…. Joining paths with "/" by hand fixed it. This is Nim's behaviour, not nimlang's.

# before: cross-compiling for Windows, `/` and parentDir use "\" on a Linux path
qjsDir = currentSourcePath().parentDir / "vendor" / "quickjs"
#   Error: cannot find: \home\user\diagrammari\experiments\python\nim\vendor\quickjs\quickjs.c
# after: join with "/" by hand
here = currentSourcePath().replace('\\', '/').rsplit('/', 1)[0]
qjsDir = here & "/vendor/quickjs"

Notes for nimlang

  • A libraries = [...] option beside extensions would say "a C ABI library for ctypes". Today it works as an extension, but the Windows file is named .pyd and the module name follows nimpy's rules: no leading underscore.
  • The Windows cross-build takes about 4 times as long as the others: 63 s against 15 to 17 s.
  • macOS and Windows wheels build on Linux, but they still need a run on their own OS. That is what the lib-demo's CI does, and diagrammari-py should copy it.

7 What changes in the plan

Recommendation

Build diagrammari-py with nimlang, and keep plug A for 0.1. The API is one call with a JSON string, the wrapper is about 20 lines and tested, and the same library can be loaded by any language with a C FFI.

Switch to plug B, or add a nimpy module beside it, when the Python API grows many small calls with Python objects (builders, callbacks). The design gave two reasons for plug A, no dependency and one wheel per platform. nimpy has both too, because it is compiled in. So the choice is closer than the design says.

  1. The build hook and cibuildwheel go. nimlang becomes a build requirement, and one Linux job builds the five wheels with NIMLANG_TARGET. A matrix on Linux, macOS and Windows installs each wheel and runs the shared spec examples. Nothing goes to PyPI until that matrix is green.
  2. The sdist builds wherever nimlang has a wheel, with no Nim installed. That leaves out musl and Windows arm64. nimlang knows their tags, but neither was tried here.
  3. nimlang pins Nim (2.2.6 today, diagrammari needs 2.0 or later). A Nim bump in diagrammari-py becomes a nimlang bump, in the same PR as the diagrammari pin.
  4. The thread fix and the Windows path fix go into diagrammari, with the C ABI move to src/mari/, before the first tag that diagrammari-py pins.

8 How it is built

From the bottom up, the pieces a wheel holds and what each one does.

Pele, inside the library

Pele 1.13.0 is one JavaScript file, pele.global.js (730 kB, MIT), vendored in diagrammari at src/mari/vendor/. capi.nim reads it with staticRead when it compiles, so the text of Pele is a constant inside the library and nothing is read from disk at run time.

QuickJS, compiled by Nim

quickjs-ng 0.18 (MIT) is vendored at a pinned commit. Nim's {.compile.} pragma hands its four C files and the shim to the C compiler, with the flags in qjsFlags: gcc or clang natively, zig cc under nimlang. No Makefile, no CMake.

The shim and the glue

mari_js_new makes a runtime and a context and evaluates Pele's bundle followed by the glue, a JavaScript function __mari that takes a JSON line, calls pele.render and, for a flowchart, pele.parse for each edge's two ends. mari_js_call calls __mari with one string and returns a malloc'd string, which mari_js_free_str frees. The runtime is made at the first draw (60 to 75 ms), kept for the life of the process, and guarded by the lock.

The procedure

draw picks the theme's font and CSS variables, asks QuickJS for Pele's SVG, applies the personal layer to a flowchart with applyLayer (std/xmltree: offsets, fills, arrow routes, a viewBox that grows to fit), adds the theme's variables to the root style, and lists the node and edge ids. With MARI_ENGINE=node it asks a Node child process instead: the same glue, read one JSON line at a time on stdin.

Plug A

Four C functions: mari_draw(request: cstring): cstring, mari_free(p: cstring), mari_pele_version(): cstring and mari_engine(): cstring. mari_draw catches Nim's errors (CatchableError) and turns them into an error answer, so nothing unwinds across the C border. The answer is copied into shared memory that mari_free releases. The last two return constants that are never freed.

Plug B

A Nim module that includes capi.nim and adds {.exportpy.} procedures. nimpy generates the module init function, converts arguments and results, and raises a Nim exception as a Python one. nimlang builds it with --app:lib --threads:on --tlsEmulation:off.

The Python package

mari/__init__.py finds native.* beside itself, loads it once with ctypes.CDLL, declares argument and result types, and wraps the answer: a dict, or DiagramError with Pele's code, line, column and snippet. If nodejs-wheel-binaries is installed it sets MARI_NODE to that Node for MARI_ENGINE=node.

The wheel

nimlang's hook compiles src/mari/native.nim for the zig target (glibc 2.17 on Linux, macOS 11.0 or 10.13), strips symbols (--passL:-s), puts the library beside __init__.py, and tags the wheel py3-none-<platform>: the library uses no Python ABI, so one wheel per platform serves every Python 3.

Versions: nimlang 0.0.3 (Nim 2.2.6, atlas), ziglang 0.17.1, nimpy 0.2.1 (114e1b9), quickjs-ng 0.18, Pele 1.13.0, Python 3.13.18 on Linux x86-64; also 3.9.25, 3.10.20, 3.11.18, 3.14.6 through uv.
