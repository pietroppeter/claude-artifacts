Nim on My iPhone

What it really takes to build a Nim app and keep it running on your own phone, with no App Store and no distribution.

Read Me First

The short answer. You do not need the paid Apple Developer Program to put an app on your own iPhone. A free Apple ID gives you a Personal Team in Xcode, and Xcode signs the app for your device. The catch is that the signature lasts 7 days: after that the app refuses to launch until you plug in and press Run again.

What you cannot avoid is a Mac with Xcode. Nim itself is happy anywhere (it writes C), but the iOS SDK, the Apple linker and code signing only exist inside Xcode.

The fastest route I would take, in one sentence: make a plain SwiftUI app from Xcode's template, compile your Nim code into a static library with one build-phase script, call it from Swift, and run it on your phone with your free Apple ID. Budget an afternoon, most of it waiting for Xcode to download.

Proof: Nim already speaks iOS (even on Linux)

This page was rendered on a Linux box with no Apple software at all. The block below really ran while the page was built: it asks the Nim compiler to generate the C for an iOS arm64 static library, then lists what came out. The Mac is only needed for the next step, turning that C into ARM machine code against Apple's SDK.

let cmd = "nim c --os:ios --cpu:arm64 --app:staticlib --noMain:on " &
          "-d:release --compileOnly --nimcache:ioscache --hints:off core.nim"
let (output, exitCode) = execCmdEx(cmd)
echo "exit code: ", exitCode, output.strip
for f in walkFiles("ioscache/*.c"):
  echo "  generated ", f.extractFilename.replace("@m", "").split("@s")[^1]
let main = readFile("ioscache/@mcore.nim.c")
echo "exports NimMain: ", "N_CDECL(void, NimMain)(void)" in main
echo "exports fib:     ", "fib" in main
exit code: 0
  generated digitsutils.nim.c
  generated system.nim.c
  generated dollars.nim.c
  generated core.nim.c
exports NimMain: true
exports fib:     true

--os:ios flips on defined(ios) everywhere in the standard library, --app:staticlib produces a .a instead of a program, and --noMain stops Nim from writing a C main(), because on iOS UIKit owns main. Your Nim code is a library that the app calls into; you call NimMain() once at startup to initialise Nim's globals.

The Apple Part: signing, explained with a calendar

iOS runs only code signed by a certificate Apple issued, for a device Apple knows about, in an app ID Apple registered. Xcode bundles all three into a provisioning profile and does it for you when Automatically manage signing is on. The only difference between free and paid that you will feel day to day is how long that profile lives.

Click days on the calendar to mark when you plugged in and pressed Run in Xcode. Green days the app opens; red days it shows "…is no longer available" and refuses to launch. Your data inside the app survives a re-sign.

Two settings on the iPhone itself trip up everyone the first time. Since iOS 16 you must turn on Developer Mode (Settings → Privacy & Security → Developer Mode, then restart), and the first launch of a free-signed app needs trusting your certificate (Settings → General → VPN & Device Management → your Apple ID → Trust).

Three Ways to Shape a Nim iOS App

Nim cannot draw an iOS screen on its own; something has to talk to UIKit. These are the three realistic options, from easiest to most Nim-pure.

A. SwiftUI shell + Nim core

Recommended to start

Xcode's template gives you a working app. Nim compiles to libnimcore.a; Swift calls your {.exportc.} procs through a one-file C header. You write a few lines of Swift for the UI and keep all logic in Nim.

Swift you write: ~20 lines · Risk: low

B. WebView shell + Nim (the wiish way)

Great if you think in HTML

A tiny Objective-C app hosts a WKWebView. The UI is HTML/JS (could even be a nimib page or Nim compiled to JS) and messages pass between JavaScript and Nim. Same signing story as A.

Native code you write: ~100 lines of ObjC, or use wiish · Risk: medium

C. Pure Nim talking to UIKit

For later, for fun

Call the Objective-C runtime from Nim (nim objc, {.emit.}, objc_msgSend) and build views in Nim. Possible, but you are writing bindings before you write your app.

Native code you write: all of it · Risk: high

And the no-Mac escape hatch. If what you really want is something made in Nim on your home screen, a web app gets there with zero Apple process: compile Nim to JavaScript (nim js, or nimib's nbJsFromCode), host the page, open it in Safari and choose Share → Add to Home Screen. No Mac, no account, no 7-day clock. It is not native (no App Store APIs, limited background work), but it is the honest fastest answer to the literal question.

Route A, in Full: the files you add to Xcode's template

Create File → New → Project → iOS → App, Interface SwiftUI, Language Swift, Team (Personal Team). Then add these four things. The Nim file is the one proven above.

1. nim/core.nim: your Nim. Every proc Swift should see gets {.exportc, cdecl.}.

proc fib*(n: cint): cint {.exportc, cdecl.} =
  if n < 2: n else: fib(n - 1) + fib(n - 2)

proc nimVersion*(): cstring {.exportc, cdecl.} = NimVersion

2. NimApp/nimcore.h: the C signatures Swift will import. Set Build Settings → Objective-C Bridging Header to this path. cint becomes Swift Int32, cstring becomes UnsafePointer<CChar>.

#pragma once
void NimMain(void);
int fib(int n);
const char* nimVersion(void);

3. A Run Script build phase (Target → Build Phases → + → New Run Script Phase, dragged above Compile Sources). It uses the variables Xcode already sets, so the same script builds for the Simulator and the phone.

# This block runs at page-build time: it renders the exact script for the
# current choices, so the flags on this page cannot drift from the prose.
proc xcodeRunScript(nimFile = "nim/core.nim", lib = "nimcore"): string =
  let nimFlags = @[
    "--os:ios", "--cpu:arm64", "--app:staticlib", "--noMain:on",
    "--mm:orc", "--threads:on", "--tlsEmulation:off", "-d:release",
    "--cc:clang", "--passC:\"$FLAGS\"", "--passL:\"$FLAGS\"",
    "--nimcache:\"$DERIVED_FILE_DIR/nimcache\"",
    &"--out:\"$PROJECT_DIR/build/$PLATFORM_NAME/lib{lib}.a\""]
  result = """set -e
export PATH="/opt/homebrew/bin:$HOME/.nimble/bin:$PATH"   # Xcode's PATH has no Homebrew
if [ "$PLATFORM_NAME" = "iphonesimulator" ]; then
  MIN="-mios-simulator-version-min=$IPHONEOS_DEPLOYMENT_TARGET"
else
  MIN="-mios-version-min=$IPHONEOS_DEPLOYMENT_TARGET"
fi
FLAGS="-isysroot $SDKROOT -arch arm64 $MIN"
nim c """ & nimFlags.join(" \\\n      ") & &" \\\n      \"$PROJECT_DIR/{nimFile}\""
echo xcodeRunScript()
set -e
export PATH="/opt/homebrew/bin:$HOME/.nimble/bin:$PATH"   # Xcode's PATH has no Homebrew
if [ "$PLATFORM_NAME" = "iphonesimulator" ]; then
  MIN="-mios-simulator-version-min=$IPHONEOS_DEPLOYMENT_TARGET"
else
  MIN="-mios-version-min=$IPHONEOS_DEPLOYMENT_TARGET"
fi
FLAGS="-isysroot $SDKROOT -arch arm64 $MIN"
nim c --os:ios \
      --cpu:arm64 \
      --app:staticlib \
      --noMain:on \
      --mm:orc \
      --threads:on \
      --tlsEmulation:off \
      -d:release \
      --cc:clang \
      --passC:"$FLAGS" \
      --passL:"$FLAGS" \
      --nimcache:"$DERIVED_FILE_DIR/nimcache" \
      --out:"$PROJECT_DIR/build/$PLATFORM_NAME/libnimcore.a" \
      "$PROJECT_DIR/nim/core.nim"

Then in Build Settings: Library Search Paths $(PROJECT_DIR)/build/$(PLATFORM_NAME), Other Linker Flags -lnimcore, and User Script Sandboxing = No (Xcode 15+ sandboxes build scripts, and this one writes outside its declared outputs).

4. Swift that calls Nim. Replace the template's two files with this:

import SwiftUI

@main
struct NimApp: App {
    init() { NimMain() }            // initialise Nim once, before any Nim call
    var body: some Scene { WindowGroup { ContentView() } }
}

struct ContentView: View {
    @State private var n = 20
    var body: some View {
        VStack(spacing: 16) {
            Text("Hello from Nim \(String(cString: nimVersion()))")
            Stepper("n = \(n)", value: $n, in: 0...35)
            Text("fib(n) = \(fib(Int32(n)))").font(.largeTitle.monospacedDigit())
        }
        .padding()
    }
}

What wiish Learned the Hard Way

The library you were thinking of is wiish, "Why Is It So Hard", by Matt Haggard (iffy), who builds the Buckets budgeting app. It aims at one Nim codebase for macOS, Windows, Linux, iOS and Android using a WebView UI. It describes itself as alpha, the last commit is from March 2024, and its own support table marks iOS Simulator builds as working while real-device builds are planned. So I would read it rather than depend on it. Reading wiish/plugins/webview.nim and the iOS template gives five lessons:

  1. Nim is a static library, Xcode is the app. wiish compiles with nim objc --os:ios --app:staticlib -d:ios, then hands the .a to a template Xcode project and runs xcodebuild. Route A above is the same shape with Swift instead of Objective-C.
  2. Pass the SDK flags to both compiler and linker. Its linkAndCompile helper adds -arch arm64, -isysroot <iPhoneOS.sdk> and -mios-version-min to both --passC and --passL. Forget one and you get baffling link errors.
  3. UIKit owns the main loop. main.m calls UIApplicationMain, and Nim's async loop is pumped by an NSTimer every 10 ms (the source itself says "this polling is terrible"). If your Nim code is synchronous, as in Route A, you skip this problem entirely.
  4. Let Xcode do the signing. wiish passes -allowProvisioningUpdates and only overrides the bundle ID and team. Automatic signing is the one part of Apple's process that already works well.
  5. Simulator flags have moved on. wiish builds the Simulator slice with --cpu:amd64, which was right for Intel Macs. On Apple Silicon the Simulator is arm64 too, and the platform (iphoneos vs iphonesimulator SDK) is what differs, which is why the script above keys off $PLATFORM_NAME.

If you want to try it anyway: nimble install https://github.com/iffy/wiish.git, then wiish doctor, wiish init hello, cd hello, wiish run --os ios-simulator.

Living with the 7-Day Clock

If you install today, these are the dates the app stops launching unless you press Run again. Computed when this page was built:

let installed = dateTime(2026, mNov, 7, zone = utc())
for week in 1..4:
  let expiry = installed + initDuration(days = 7 * week)
  echo &"re-sign #{week}: before {expiry.format(\"ddd d MMM\")}"
re-sign #1: before Sat 14 Nov
re-sign #2: before Sat 21 Nov
re-sign #3: before Sat 28 Nov
re-sign #4: before Sat 5 Dec

Three things make it bearable. After the first cable install, Xcode can install over Wi-Fi when both are on the same network (Window → Devices and Simulators → Connect via network). Re-running only re-signs, it does not wipe data. And if the clock really annoys you after a few weeks, that is exactly the moment the $99 program earns its price; nothing you built has to change except the Team dropdown.
