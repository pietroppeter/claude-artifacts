Skill issues, explained for Nim folks

When a coding agent gets your library wrong, the fix is usually a Markdown file: a skill. A team at Bauplan Labs stopped hand-tuning theirs and started optimizing them, like hyperparameters, against hundreds of tasks whose results a program can check. This page walks through how, and what the same trick would look like for Nim and nimib.

This is an explainer of “Skill Issues”: Data-Centric Optimization of Lakehouse Agents by Nicole Rose Schneider (University of Maryland), Davide Ghilardi (Università Milano-Bicocca), Giacomo Piccinini and Jacopo Tagliabue (Bauplan Labs), at the VLDB 2026 workshop on Agentic Data Systems. The code is open source (MIT) at BauplanLabs/skill-issues. Notes marked For nimib are ours, not the paper's.

  • A coding agent setup is mostly fixed: you pick Claude Code and a model, and you cannot retrain either. What you can change is text: CLAUDE.md and the skills. So treat that text as the parameters to optimize.
  • To optimize you need a score, and a score needs a check. Bauplan is a lakehouse with git for data: every write an agent makes becomes a commit you can inspect. So instead of asking "does the answer look right?", the checks ask "did the data change the way it should?"
  • They generate tasks together with their verifiers, run the agent in sandboxes on a throwaway branch, score each run, and let an optimizer (GEPA) rewrite the skill. Repeat.
  • Every skill improved on held-out tasks. Skills used in tasks that need several skills improved least: the next step is to optimize skills together.

Why a Nim person should care

The paper's starting point will sound familiar: "Bauplan APIs are not yet well represented in the training set, users' prompting abilities vary widely, and the new affordances call for revised best practices." Replace Bauplan with Nim, or with nimib, and it is the same situation. Models have seen far more Python than Nim, and far more Jupyter than nimib. Skills are how we close the gap.

Pietro's skills repo is exactly these two boxes: a CLAUDE.md and plugins of skills (nimib, nimib-theme, nimib-blocks, nimibook, publish-artifact, …). Everything this paper does to Bauplan's skills could be done to those.

From matching outputs to checking state

The paper's central observation: on a branching lakehouse, evaluating an agent stops being an output-matching problem and becomes a state-verification problem.

Two Bauplan features make that work. It is headless: everything (running pipelines, creating tables, reading logs) is an API call, through a CLI or a typed Python SDK, so a verifier can use the same calls the agent uses. And it is git for data: branches, commits and merges over tables. When the agent runs a pipeline on a branch, each write is a commit, and the final merge into main is one more. Reading the pipeline code, you can list the commits a successful run must leave behind. The paper calls this the isomorphism between pipeline code and data commits, and it is what lets a program check write tasks ("ingest this file", "fix this table"), not just read-only ones like text-to-SQL.

The paper

"A candidate skill is rewarded only when the agent changes the lakehouse in the intended way." Checking state also limits cheating: an agent that says it merged, but did not, gets no credit.

For nimib

A nimib document has the same property on a small scale. It is code, and running it writes an HTML page that follows from the code. So the page is state you can inspect. Pietro's nimib skill already ships nbcheck.nim, which builds a document and checks the rendered HTML, and nimib-theme ships phonecheck.js, which loads the page at 390 px and checks that code blocks fit. Those are verifiers of state. Nim adds one more check for free: the paper notes that "a statically checkable SDK reduces round-trips", and in Nim the compiler checks the document before it runs.

One task, start to finish

Every benchmark task runs through the same six steps (the paper's Table 1). The fixed life-cycle is what makes it safe to let the agent write: it only ever writes on a branch made for it. Switch the tab to see the same steps for a nimib page.

Three ways to catch an agent

Each run is checked at three levels:

  • Trace: what the agent did. Did it load the expected skill? Did it call the expected commands (CLI or SDK, either is fine)? Did it avoid forbidden ones, like bauplan run in a read-only task?
  • State: what changed. Does the branch exist? Is a table unchanged that should be? For write tasks, a Python script uses the SDK to check the result commit by commit and exits non-zero, with an explanation, when something is off.
  • Response: what the agent said. Hard checks (a string, a regex) and soft ones: a rubric that an LLM judge grades, for free-form answers like a data exploration.

The score of a run, its reward, is the share of checks that pass, from 0 to 1. Try placing these cases. Some are from the paper, some are from Pietro's own nimib skill tests.

Where the tasks come from

You cannot optimize against five hand-written examples, so the authors generate the benchmark, carefully. Real usage sets the mix: here is what agents actually call on Bauplan (a May 2026 sample of anonymized production logs, the paper's Table 2).

Raw counts are only a prior. Today's traces are shaped by today's skills (well-documented calls show up more), and some rare calls matter a lot for safety, so every API is covered on purpose. The authors also look at whole sessions: a branch, an import, a check query and a merge in a row read as a safe ingestion. A model can infer the intent behind a session and turn it into a task template (they call this inverse planning).

Tasks vary along three axes: the scenario (six kinds, read or write), the persona (data engineer, analyst, scientist), and how explicit the prompt is. Vague prompts model novices, detailed ones model experts who name tables, columns and acceptance criteria. Here is the same intent at the three levels, for a nimib task:

Explicitness Prompt
vague make me an IMIB page with word counts
medium Make a nimib document that counts word frequencies in a paragraph and shows the top 5.
detailed word_freq.nim: one nbCode counts words with a CountTable, echo the top 5, prose interpolates the top word; build word_freq.html; no raw HTML.

An LLM (GPT-5.5 was the one that could write a consistent task and verifier in one go) emits one task at a time through a typed tool call. Each is validated, for example "commands must correspond to real CLI arguments", and read-only tasks must forbid at least one write and assert that nothing changed. Invalid ones are thrown away and regenerated. Then domain experts sample and read tasks by hand.

For nimib

The vague row is not a joke: Pietro dictates, and voice recognition turns "nimib" into "IMIB". A skill that only works for detailed prompts fails its most frequent user. The explicitness axis is a good idea for any Nim skill benchmark.

The optimizer, and what it found

The optimizer is GEPA (optimize anything), which evolves text by reflecting on failures. It takes a seed skill, an evaluation function (run the agent in a sandbox on tasks that need the skill, return the reward) and a description of the goal. It proposes new versions of the skill, reading the error traces as hints.

For each of the six skills, the tasks that need it are split 70 / 15 / 15: GEPA learns on the first part, picks its best candidate on the second (validation), and the third (test) is held out to measure the result. The agent is Claude Code with Sonnet 4.6. Here are the curves, redrawn from the paper's Figure 4:

The paper

For every skill, GEPA found a candidate that beats the seed on validation and on held-out tasks, by 12.0% on average and by up to 28.6%. Skills whose tasks need several skills at once improved only a little when optimized alone.

What changed in the text? The optimizer added detail: pointers to the docs, phrases telling the agent not to invent or guess flags, good practice like Write-Audit-Publish on an isolated branch, and better description lines when a check failed because the agent never loaded the skill.

Our reading

Picking by validation, as the method says, gives about +9.6% on average in our reading, and debug-and-fix-pipeline gets slightly worse on test (−1.4%). The headline "up to 28.6%" matches the best test point of data-quality-checks (candidate 9, +28.5% in our reading), not the candidate validation would pick there (8, +22.5%). Our readings are by eye, to about ±0.01, and the paper does not say how its 12.0% average was computed, so take this as a question to ask the authors, not a finding.

So 8 task-verifier pairs with 54 checks, about the size of the paper's first version (its v1 abstract reported results on 25 tasks). The paper ends with 780. Here is the shape of one pair and its reward, in Nim. The code runs when the page is built:

type
  Level = enum trace, state, judge
  Check = object
    level: Level
    what: string

let task = %*{
  "task_name": "nimib_word_frequency_page",
  "category": "write_new_page",
  "explicitness": "vague",
  "prompt": "make me an IMIB page with word counts",
  "expected_skills": ["nimib"],
  "forbidden_actions": [{"pattern": "cdn\\.jsdelivr|highlight\\.min\\.js",
                         "reason": "pages are self-contained"}]}

let checks = @[
  Check(level: trace, what: "the nimib skill was loaded"),
  Check(level: state, what: "word_freq.html exists"),
  Check(level: state, what: "it shows code output (nb-output)"),
  Check(level: state, what: "nbcheck passes, phonecheck passes at 390px"),
  Check(level: judge, what: "numbers in the prose come from the code")]

func reward(passed: openArray[bool]): float =
  passed.countIt(it).float / passed.len.float

echo task["prompt"].getStr, "  (", task["explicitness"].getStr, ")"
# an agent that wrote a page but never ran it, and said it did
let passed = [true, true, false, false, true]
for i, c in checks:
  echo (if passed[i]: "pass " else: "FAIL "), ($c.level).alignLeft(6), c.what
echo "reward: ", reward(passed), "   (output matching on \"Done!\" would give 1.0)"
make me an IMIB page with word counts  (vague)
pass trace the nimib skill was loaded
pass state word_freq.html exists
FAIL state it shows code output (nb-output)
FAIL state nbcheck passes, phonecheck passes at 390px
pass judge numbers in the prose come from the code

The rest of the loop exists too. The skill-issues repo separates a domain-agnostic engine (src/core) from domains (src/domains), and just new-domain <name> copies a template to fill in: scenario and task prompts, a schema, a Docker environment with the skills, a test script. A nimib domain would need:

  1. Tasks from real sessions. Pietro's project threads are sessions: an ask, a sequence of commands, a merged PR or a complaint. That is the input for inverse planning, and the complaints ("code spills out of its box on my phone") become checks.
  2. Verifiers that read state. nim r compiles the document (the static check), nbcheck reads the HTML, phonecheck loads it at 390 px, and regexes keep raw HTML out of the source.
  3. An adapter. The paper runs tasks with Harbor on Modal sandboxes and scores with its own checks; Pietro's cases use claude plugin eval graders. One format would have to be translated into the other.
  4. Multi-skill tasks, with care. A page like this one uses nimib, nimib-blocks, nimib-theme and publish-artifact together. The paper found that optimizing one skill at a time barely helps such tasks, so optimizing them jointly is the interesting part.
Careful

We have not run the skill-issues code on nimib: the list above is a plan, not a result. It needs Modal and LLM API keys, and every optimization run costs many agent runs.

Caveats

  • Preliminary, by the authors' own word. One agent (Claude Code) and one model (Sonnet 4.6). A skill tuned for one model may not transfer to another.
  • Small held-out sets. Each skill's test set is 15% of its pool of tasks, so a few tasks move the reward by points. Several curves zig-zag by as much as the gains.
  • The headline moved. The first version of the abstract said 31.9% on 25 tasks; the current one says up to 28.6% on hundreds. The body reports 12.0% on average.
  • Synthetic tasks, checked by sampling. An LLM wrote both tasks and verifiers; experts read a sample. A wrong verifier rewards the wrong behaviour, and the optimizer will find it.
  • Longer skills cost context. The optimizer has no reason to keep skills short unless the goal says so; 27× longer means more tokens on every task that loads them.
  • Bauplan's own features do much of the work. The authors say so: without headless APIs and git for data, fine-grained write checks would not have been possible. Other domains need their own way to read state (for nimib: the HTML).
