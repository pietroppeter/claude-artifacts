A Nim library in a Python wheel

The Nim side is compiled with nim c --app:lib into libmari.so. It exports a few plain C functions: mari_draw takes a JSON request (Mermaid text, layer, options) and returns a JSON answer (the SVG, or Pele's error), mari_free releases the answer, and mari_pele_version and mari_engine report the Pele version and the engine. Python loads the library with ctypes from the standard library. There is no nimpy and no compiled Python extension, so one wheel works with every Python 3 on a platform.

proc mari_draw(request: cstring): cstring {.exportc, dynlib, cdecl.}
proc mari_free(p: cstring) {.exportc, dynlib, cdecl.}

A small hatchling build hook runs Nim during uv build and tags the wheel py3-none-<platform>:

$ uv build --wheel
{{build}}

$ unzip -l dist/diagrammari-0.0.1-py3-none-linux_x86_64.whl
{{wheel}}

The library is 2.4 MB: QuickJS (about 1.2 MB, see exhibit H), Pele's bundle (730 kB, embedded with staticRead) and the Nim code. The widget gets its own copy of Pele (pele.global.js) because the browser draws too. The compressed wheel is 1.3 MB.

EXHIBIT C

The layer, exported headless

Below are the two files that run wrote: plain.svg is what Pele draws, and personal.svg is the same Mermaid text with this layer applied:

{"theme": "isotype", "arrows": "curve",
 "nodes": {"ship": {"dy": 120, "fill": "#c8402b"}},
 "edges": {"L_review_draft_0": {"route": "bezier", "c1": [-30, -80], "c2": [30, -80]}}}

The layer is keyed by Mermaid's node ids and by Pele's edge ids (L_review_draft_0), and it stores offsets, not positions. If you add a line to the text, Pele lays out the diagram again and the layer still applies. The Nim code (layer.nim) works on the SVG text with std/xmltree and uses the same geometry as the browser editor.

EXHIBIT D
seen in marimo 0.25.2

The editor in marimo

The editor is an anywidget: one ES module (Pele's bundle followed by about 250 lines of editor) and three synced traits, source, layer and svg. marimo runs any anywidget through mo.ui.anywidget, and a cell that reads editor.value runs again on every edit. Here Playwright dragged Ship down, clicked the dotted arrow, picked bezier and switched the theme. The second cell showed the layer and the SVG exported by Nim from it, as you went.

editor = mo.ui.anywidget(mari.Diagram(src).edit())
# next cell, reruns on each edit:
layer = editor.value["layer"]
mari.Diagram(src, layer).save("from_marimo.svg")

The editor in a browser tab

To work without a notebook, from a script or the REPL, d.edit_in_browser() serves the same module on 127.0.0.1 with a stand-in for the anywidget model, opens a tab, and blocks until you press Done:

diagrammari editor: http://127.0.0.1:8765/
layer back in Python: {'theme': 'pele', 'arrows': 'pele', 'nodes': {'b': {'dx': 68, 'dy': 124}}, 'edges': {}}

This uses only http.server and webbrowser from the standard library, so it adds no dependency.

Why Node was needed, and how QuickJS replaced it

  
Pele is a JavaScript program, and Nim cannot run JavaScript by itself, so something has to execute it.
  diagrammari (PR #1) starts one Node process and talks to it in JSON lines. That works wherever Node is installed, but for Python it means
  a 61 MB download (204 MB installed) when Node isn't already there.

  
QuickJS is a small JavaScript engine written in C (quickjs-ng 0.18, MIT). It runs Pele unchanged. I first checked that with the
  quickjs package from PyPI:

  
{{qjs}}

  
Then, with Pietro's go, I compiled it into the Nim library. Four C files are built by Nim's {.compile.} pragma, with no CMake, and a
  40-line C shim gives Nim four functions: make a context, evaluate Pele, call a function with a string, and free. The sources are vendored and pinned
  to a commit. The test below draws the same four diagrams from Nim and compares them with Node's:

  
{.compile(qjsDir / "quickjs.c", qjsFlags).}
{.compile(qjsDir / "libregexp.c", qjsFlags).}
{.compile(qjsDir / "libunicode.c", qjsFlags).}
{.compile(qjsDir / "dtoa.c", qjsFlags).}
{.compile(here / "mari_qjs.c", qjsFlags).}

  
{{qjs_nim}}

  
The four sources were a flowchart, a sequence diagram, a pie and a class diagram. The test binary is 2.1 MB and needs only libc and libm.
  The same engine can draw nimib pages at build time too, which is a BACKLOG item for the Nim library.

CASE 2

  
verdict · first degree

  
One repo or two?

  
The question. Should the Python package live in the diagrammari repo, in a python/ folder, or in a repo of its own
  (say diagrammari-py)? A separate repo looks cleaner. To decide, ask what could kill this project in a year. Each layout lets a different
  culprit in, so we find the likeliest one first.

  
The victim. A Python user. They run uv add diagrammari, and their diagram comes out different from the same text in a nimib page.
  Or the editor moves a box and the export doesn't, or a Pele fix shipped in Nim three months ago never reached PyPI.


  

    
Suspect 1: Drift

    
Two copies of anything that must match: the Pele bundle and its version, QuickJS and its commit, the C ABI, the layer's JSON,
    the spec. Drift only needs two repos and a busy week. In a separate repo, every change to the ABI or the layer is two PRs in a set order, and
    every Pele upgrade is done twice. No alibi in the two-repo layout. In one repo, a single PR changes the Nim code, the ABI, the widget and
    the spec together, and the same CI checks the Nim tests and the wheel.

  

  

    
Suspect 2: Clutter

    
A Nim repo grows a pyproject.toml, a hatch hook, a wheels workflow and a python/ folder, so Nim contributors
    see Python and Python contributors see Nim. That's real, but small. Nimble installs only srcDir (src/), so Nim users never get the Python
    files, and the Python tree is one folder plus one workflow. Guilty of untidiness, not of murder.

  

  

    
Suspect 3: Tangled releases

    
Nim and Python may want different release speeds. One repo can still tag them apart (v0.2.0 for nimble, py-v0.2.0
    for PyPI, each starting its own workflow), and PyPI trusted publishing is set per repo and workflow, so that works. A separate repo makes
    this easier, but drift (suspect 1) follows the moment the two release speeds differ. Alibi holds.

  

  

    
Suspect 4: The build that can't see the Nim code

    
The proof of concept builds from experiments/python/ and reaches up to ../../src for the Nim code and Pele. A wheel
    built in CI is fine, but an sdist from a subfolder can't include files from the folder above it. So in one repo, pyproject.toml goes at the
    root, next to mari.nimble, with the Python code in python/mari/. In a separate repo you need a git submodule or a pinned clone of
    diagrammari just to build. Caught in both layouts. One repo with the pyproject at the root disarms it.

  

  

    
Suspect 5: Identity

    
Is diagrammari a Nim library with Python bindings, or a product with two front doors? The PyPI page and the docs would say "diagrammari"
    either way. One repo means one README, one set of issues, one specs page and one devlog: one story. Not a threat in one repo.

  


  

    
Verdict: same repo. The culprit is drift, and only the two-repo layout lets it in. The Python package is a second front door to the same
    library: the same Pele, the same QuickJS, the same layer, the same spec. Things that must match belong in one place, checked by one CI.

    
The layout: pyproject.toml at the root (distribution diagrammari, import mari), Python code in
    python/mari/, the C ABI in src/mari/capi.nim next to the library, and wheels built by .github/workflows/wheels.yml on
    py-v* tags. The Python spec lives in openspec/specs/python/ with the others.

    
Court: Claude sat as the jury, in the first degree. Pietro is the corte d'appello, the second degree; he appealed. See the appeal.

    
When to reopen the case: if the Python side grows its own large surface, such as Python builders, Pyodide or a JupyterLab extension with a
    build, or gets its own maintainers. Splitting out later is a git subtree split; merging two drifted repos back together is much harder.

  






  
CASE 2 · APPEAL

  
reformed on appeal

  
Corte d'appello: the same case, with agents doing the work

  
The appeal. Pietro objects that the first degree judged the case by pre-AI rules. Drift kills when people forget the second repo. In this project,
  agents keep twelve repos moving at once, so the case is reopened with that as the premise.


  

    
Drift, cross-examined

    
Drift needed two things: a change that has to land in two places, and nobody remembering to do the second one. Agents remove the second
    condition, but only when something asks them. The coordination cost (two PRs, a Pele bump done twice) is now minutes of agent time instead of an
    evening of yours. What agents don't remove is silent drift, a mismatch nobody asks about. So drift has to be made loud: the second repo
    pins diagrammari to a tag, its CI runs the shared spec examples against that pin, and a routine opens the bump PR when diagrammari tags a
    release. Then drift is a version lag you can see, not a mismatch you discover. Downgraded from murder to a misdemeanour, if the pin and the
    routine exist.

  

  

    
New witness: the agents themselves

    
This morning three threads worked on diagrammari at once: the build PR, the series PR and this one. They had to coordinate over
    BACKLOG.md to avoid a conflict. With one repo per front door, a Python thread and a Nim thread don't share a branch, a backlog or a CI run.
    Each repo also gets an AGENTS.md for one toolchain: atlas, nimble and nimib pages there; uv, cibuildwheel, Jupyter and marimo here. A focused
    checkout is less context per task, so fewer mistakes. Testifies for two repos.

  

  

    
New witness: CI time

    
A wheel matrix (Linux, macOS, Windows) with Nim and QuickJS compiled in takes about 15 minutes per run. In one repo, every Nim docs fix
    either waits for it or needs path filters. In two repos, each runs its own CI, and agents iterate faster on each side. Testifies for two repos.

  

  

    
Suspect 4 again: the build that can't see the Nim code

    
A pinned dependency solves it: the Python build fetches diagrammari at the pinned tag (git dependency or atlas lock), and the sdist
    vendors that snapshot. That's the same idea as pinning Pele and QuickJS, which diagrammari already does. Disarmed by the pin.

  


  

    
Ruling on appeal: two repos, with a contract. In an AI world the cost that made one repo win, keeping two places in step, is cheap, and the
    costs of one repo (agents colliding, mixed toolchains, slow shared CI) matter more. The ruling holds only under three conditions, or drift is back:

    
    
      
  1. diagrammari owns everything that must match: the Nim library, the C ABI (src/mari/capi.nim), Pele, QuickJS, the layer engine,
      the editor's JavaScript (also for nimib pages, a BACKLOG item), and the specs with their examples.
    2. 
      
  2. diagrammari-py owns only the Python side: pyproject.toml, the Python API and widget wrapper, the wheels workflow and the notebook docs.
      It pins diagrammari to a tag, and its CI runs the shared examples against the pin.
    3. 
      
  3. A routine closes the loop: when diagrammari tags a release, an agent opens the bump PR in diagrammari-py, and nothing ships to PyPI until it's green.
    4. 
    

    
Open detail: which org gets the repo, pietroppeter/diagrammari-py or nimib-land/. It should follow wherever diagrammari ends up.

    
The first degree isn't wrong about drift; the appeal changes who pays to prevent it. In the proposals, add-python-package is
    updated to this layout: the C ABI stays in diagrammari, and the package moves to its own repo.
