Cartographer, in Nim

Your team's coding agents each learn things and forget them. Cartographer gives them one shared wiki they can all read and grow, but can't break. This page studies it, rebuilds its core in about 400 lines of Nim, compares it with the alternatives, and asks whether it fits a project with many repos and many teams.

The short answer

The idea is a good fit for a multi-repo, multi-team project. Cartographer itself is worth a pilot, not a rollout. The pattern it builds on (an LLM-maintained Markdown wiki, stored in the Open Knowledge Format) is cheap to adopt and easy to leave, because the knowledge is plain files in git. What Cartographer adds is a server that refuses bad writes and records who changed what and why. That matters most when several teams' agents write to the same knowledge. Against it: it's a pre-1.0 personal project with one maintainer, and it gives you a server to run.

And yes, "OKF LLMWiki" is the same family. LLM Wiki is Andrej Karpathy's pattern (April 2026), and OKF is Google Cloud's Open Knowledge Format (June 2026), which formalizes that pattern as a file format. Cartographer says it combines the two. I couldn't find a single product called "OKF LLMWiki". The closest match is a small demo repo, okf_llm_wiki, which lays the same knowledge out both ways. Jump to the fit analysis.

01 · WHAT IT ISCartographer in one picture

Cartographer is "a shared, git-backed wiki your team's AI agents maintain but can't break — Claude Code, Codex, OpenCode and any MCP client." It is one Go binary, Apache-2.0, by GitHub user BeppeTemp, and it describes itself as "Pre-1.0" and "a personal project maintained on a best-effort basis". When I read it, the repo had 924 commits and 54 stars.

Its README names three fixes teams usually try, and says why each falls short:

  • RAG "retrieves, but nothing accumulates."
  • A folder of Markdown the agent edits freely ends in "broken links, lost history and silent corruption."
  • Skills and instructions "get hand-copied into .claude/, .codex/, .kiro/… and drift apart."

Its answer is one rule: "The agent uses MCP tools; the server owns filesystem writes and validation." Agents never open the files. They call tools such as concept_read and concept_write, and the server checks every write before it lands. Each write becomes one git commit, so nothing is lost and every change can be traced.

Beyond that core, the docs describe a lot of surrounding machinery. I read the README, overview, FAQ, data plane and control plane docs:

  • Layout. An Atlas is one knowledge base (KB) and one git repo. Under data/ are Maps, which are thematic folders, and Journals, which hold dated pages named YYYY-MM-DD-slug. Each page is a Concept. A folder's _map.md can declare a contract: which concept_types are allowed and which required_fields each page needs. A page's id is its path, and that id is its identity.
  • Beyond knowledge. The same repo also holds skills/, agents/ (subagents), hooks/, mcp/ descriptors, SOPS-encrypted secrets/ and instructions.md. cartographer sync installs them into each client, so every agent on the team is configured from one place.
  • Tools. About 60 MCP tools covering reading, keyword search (the docs say "keyword search only"), writes (including an atomic concept_batch), graph queries (personalized PageRank), governance (validate, lint, kb_review, gate_check), ingest and conflicts.
  • Teams. One HTTP server can serve several KBs, with bearer tokens scoped per KB and per map (kb:<name>:r or rw). Commits carry Reason:, Agent: and author trailers. When two machines' changes conflict, the KB is marked degraded and someone must pick ours, theirs or edit for each page. The FAQ says: "It is not a silent last-write-wins."
  • Its own limits, as stated. Search has no model-backed mode, sync is "not atomic across clients", and: "If your knowledge fits in one repository and one person, a plain instruction file is simpler and you should use it."

I couldn't open the project site beppetemp.github.io/cartographer from my sandbox because the network policy blocked it. Everything above comes from the GitHub repo and its docs/ folder. I didn't read the changelog, the decision records or the sync and concurrency docs.

02 · WHERE IT COMES FROMLLM Wiki + OKF, the "OKF LLMWiki" question

Cartographer's overview says it combines "Karpathy's LLM Wiki pattern" with "Google's Open Knowledge Format (OKF)". Both are recent:

LLM Wiki (Karpathy's gist, created April 4, 2026) is "an idea file": instead of RAG re-deriving answers from raw documents on every question, an LLM "incrementally builds and maintains a persistent wiki", so "the wiki is a persistent, compounding artifact." It has three layers: raw sources, which are immutable; the wiki; and the schema, a CLAUDE.md or AGENTS.md that tells the agent the rules. It also has three operations: ingest, query and lint. Two files are special. index.md is a catalog the agent reads first, and log.md is an "append-only record of what happened and when".

OKF (Google Cloud blog, June 12, 2026) is "an open specification that formalizes the LLM-wiki pattern". The spec, now at v0.2, is short: a bundle is "a directory of markdown files with YAML frontmatter", and type "is the only always-required key". index.md and log.md are reserved. Links are paths relative to the bundle that start with /. Consumers "MUST tolerate broken links". That last point is where Cartographer goes further: it validates a bundle on every write, so it is stricter than OKF requires.

So "OKF LLMWiki" names the same family of ideas: the LLM Wiki is the workflow, and OKF is the file format. That phrasing comes from real-jiakai/okf_llm_wiki, a 5-star demo that organizes one knowledge base both ways. I found no product by that exact name. If you saw it somewhere specific, send me the link and I'll check whether it's something else.

03 · THE MINIMAL VERSIONcarto.nim: the core, in one file

To understand the idea, I rebuilt the part that makes Cartographer more than "a folder of Markdown": a server that owns the writes. carto.nim is one file with no dependencies beyond the Nim standard library and the git command. It keeps these parts:

OKF pages: Markdown + frontmatter, type required parseConcept, render, round-trip check on every write
Agents use tools; the server owns the files write is the only way a page changes
Folder contracts in _map.md (concept_types, required_fields, journals) mapFor, problems; mapCreate is for people only, with no tool for agents
Optimistic concurrency, stale_write the etag is the page's git blob id; if_match must match
One git commit per write, with Reason: and Agent: trailers commit, history
index.md + log.md (OKF reserved files) regenerated on every write; log is newest first
Keyword search, links graph, lint search, neighbors, lint
MCP server carto serve: JSON-RPC 2.0 over stdio, 7 tools

I also added one thing aimed at a multi-repo project, which I didn't find in Cartographer's docs. A page can cite code with sources: [repo:path]. The server pins each source to the file's current git blob, and lint reports source_drift once that code changes. Documentation that silently goes stale is the main way a knowledge base dies across many repos.

Here is the write path. Everything else in the file supports it:

proc write*(kb: Kb, c: Concept, ifMatch = "", reason = "", agent = "unknown"): string =
  ## The only way a page changes. Refuses with a code, or commits and returns the new etag.
  let cur = kb.etag(c.id)
  if cur != ifMatch:
    if ifMatch.len == 0:
      refuse("stale_write", &"`{c.id}` already exists (etag {cur[0 ..< 7]}); read it and pass its etag as if_match")
    if cur.len == 0: refuse("stale_write", &"`{c.id}` does not exist; create it with an empty if_match")
    refuse("stale_write", &"`{c.id}` changed since you read it (now {cur[0 ..< 7]}); read it again and merge")
  let ps = kb.problems(c)
  if ps.len > 0: refuse(ps[0].split(':')[0], ps.join("\n"))
  var c = c
  if "sources" in c.meta:
    c.meta["sources"] = "[" & c.meta["sources"].list.mapIt(kb.pin(it)).join(", ") & "]"
  let text = c.render
  let back = parseConcept(c.id, text)   # what we write must read back identically
  if back.meta != c.meta or back.body != c.body: refuse("round_trip", &"`{c.id}` does not survive a re-read")
  createDir(kb.pathOf(c.id).parentDir)
  writeFile(kb.pathOf(c.id), text)
  let verb = if cur.len == 0: "concept_new" else: "concept_write"
  kb.logEntry(&"{verb} [{c.id}](/{c.id}) by {agent}: {reason}")
  kb.regenIndex
  kb.commit(&"{verb}: {c.id}", reason, agent)
  kb.etag(c.id)

The checks it runs come from problems. These are the same checks lint later runs over the whole KB:

proc problems*(kb: Kb, c: Concept, pending = initHashSet[string]()): seq[string] =
  ## Everything wrong with a page, as `code: message` lines. Empty means it may be written.
  if not validId(c.id):
    result.add &"invalid_id: `{c.id}` must be 1-3 kebab-case segments and not a reserved name"
  for k, v in c.meta:
    if not k.allIt(it in {'a'..'z', '0'..'9', '_'}): result.add &"bad_key: `{k}`"
    if '\n' in v: result.add &"nested_frontmatter: `{k}` spans lines"
  let typ = c.meta.getOrDefault("type")
  if typ.len == 0: result.add "missing_type: OKF requires a `type` in the frontmatter"
  let m = kb.mapFor(c.id)
  if m.meta.len > 0:
    let allowed = m.meta.getOrDefault("concept_types").list
    if allowed.len > 0 and typ.len > 0 and typ notin allowed:
      let names = allowed.join(", ")
      result.add &"type_not_allowed: `{m.id}` takes {names}, not {typ}"
    for f in m.meta.getOrDefault("required_fields").list:
      if c.meta.getOrDefault(f).len == 0: result.add &"missing_field: `{m.id}` requires `{f}`"
    if m.meta.getOrDefault("kind") == "journal":
      let n = c.id.split('/')[^1]
      if n.len < 11 or n[4] != '-' or n[7] != '-' or n[10] != '-':
        result.add &"journal_name: pages in `{m.id}` are named YYYY-MM-DD-slug"
  for l in c.body.links:
    if not kb.exists(l) and l notin pending: result.add &"broken_link: `{l}` does not exist"

06 · WHAT THE MINIMUM LEAVES OUTWhere the other 90% of Cartographer goes

carto.nim shows the core idea, and it leaves out most of what you'd need to run this for real teams. Here's what Cartographer documents and this version skips:

  • A server for many people. Cartographer has an HTTP mode with bearer tokens scoped per KB and per map, and serves several KBs from one process. carto is one local process per user. With git underneath, each person would run their own and push and pull, and then you need Cartographer's answer to conflicting merges (degraded state, git_conflict_resolve).
  • Atomic multi-page writes (concept_batch). In the walkthrough, the decision, runbook and service page took three commits and had to be written in dependency order.
  • Agent configuration as knowledge. Syncing skills/, agents/, hooks/, MCP descriptors and SOPS secrets into every client. For a team lead this may be the most useful part, because it stops each developer's .claude/ from drifting.
  • Lifecycle and trust fields (status, superseded_by, confidence, provenance), supersede, archive, review gates, the read-only web UI ("Atlas"), a graph ranked by personalized PageRank, and a signed audit log.

08 · FITFor a multi-repo, multi-team project

I don't know your project's details, so this assumes several teams, each owning a few repos, with developers using coding agents (Claude Code, Codex and others), and knowledge that crosses repo boundaries: contracts between services, decisions, runbooks and onboarding.

Where it helps most

  • Cross-repo knowledge with no home. "Why do we retry this way" lives in Slack, in one person's head, or in one repo's CLAUDE.md. A shared KB with one folder per team and a journal of decisions gives it a home that every agent reads at the start of a session.
  • Many writers, little trust. If agents on several teams will write, the guardrails are the point: required type and owner, no broken links, no blind overwrites, and an audit trail that names the agent and the reason. This is the gap between Cartographer and a plain folder.
  • One agent setup for everyone. Shipping the team's skills, subagents and instructions from one repo to every client fixes the drift between developers' .claude/ and .codex/ folders. You may find this useful even if you use nothing else.
  • Easy to leave. It's OKF Markdown in git. If Cartographer stalls, the bundle stays readable by people, by other OKF tools, and by any agent with plain file access.

What to watch

  • Bus factor. It's a pre-1.0 personal project, maintained on a best-effort basis, with breaking changes in minor versions. Pin a version and don't put it in the critical path yet.
  • A server to run. You'd need the HTTP mode, tokens, backups, and someone who owns it. The local mode is one person's KB.
  • KBs don't link to each other. The docs say "no cross-links between different KBs". For one project, use one KB with a map per team, not one KB per team, or the cross-team links you want most won't be possible.
  • Drift from code. The KB lives outside the code repos. Unless something ties pages to code (like the sources check above, or a CI job that asks for KB updates on API changes), it will drift the way wikis always do.
  • Search is keyword-only. That's a deliberate choice, and fine for a curated wiki. It's weak for fuzzy recall over a large corpus.

What I'd do

  1. Start with the format, not the server. Create one kb-<project> repo as an OKF bundle with services/, teams/<team>/ and a decisions/ journal. Add a short AGENTS.md with the rules and link it from every code repo's AGENTS.md/CLAUDE.md. Run a lint in CI, either carto's or a 50-line script. This costs a day and settles whether agents and people actually use the KB.
  2. Pilot Cartographer with two teams for two to four weeks once more than a couple of people's agents are writing. Watch for refused writes (that's the guardrails working), conflicts, merge pain, and whether cartographer sync of skills saves real time.
  3. Decide on evidence. If agents edit freely and quality holds, the plain bundle may be enough. If you see broken links, overwrites or nobody knowing where a claim came from, that's what Cartographer is for. Either way, nothing is wasted, because the files are the same.

Questions that would change this: How many people's agents would write, as opposed to read? Do you already run a docs portal such as Backstage or Confluence that this must coexist with? Can your teams run a shared internal service, or must everything be local and git-only?

nbRawHtml: """<h2 id="fit"><span class="num">08 · FIT</span>For a multi-repo, multi-team project</h2>"""

nbText: """
I don't know your project's details, so this assumes several teams, each owning a few repos, with developers using coding agents
(Claude Code, Codex and others), and knowledge that crosses repo boundaries: contracts between services, decisions, runbooks and onboarding.

**Where it helps most**

- **Cross-repo knowledge with no home.** "Why do we retry this way" lives in Slack, in one person's head, or in one repo's `CLAUDE.md`.
  A shared KB with one folder per team and a journal of decisions gives it a home that every agent reads at the start of a session.
- **Many writers, little trust.** If agents on several teams will write, the guardrails are the point: required `type` and `owner`,
  no broken links, no blind overwrites, and an audit trail that names the agent and the reason. This is the gap between Cartographer and a plain folder.
- **One agent setup for everyone.** Shipping the team's skills, subagents and instructions from one repo to every client fixes the
  drift between developers' `.claude/` and `.codex/` folders. You may find this useful even if you use nothing else.
- **Easy to leave.** It's OKF Markdown in git. If Cartographer stalls, the bundle stays readable by people, by other OKF tools, and by any agent with plain file access.

**What to watch**

- **Bus factor.** It's a pre-1.0 personal project, maintained on a best-effort basis, with breaking changes in minor versions.
  Pin a version and don't put it in the critical path yet.
- **A server to run.** You'd need the HTTP mode, tokens, backups, and someone who owns it. The local mode is one person's KB.
- **KBs don't link to each other.** The docs say "no cross-links between different KBs". For one project, use **one KB with a map
  per team**, not one KB per team, or the cross-team links you want most won't be possible.
- **Drift from code.** The KB lives outside the code repos. Unless something ties pages to code (like the `sources` check above,
  or a CI job that asks for KB updates on API changes), it will drift the way wikis always do.
- **Search is keyword-only.** That's a deliberate choice, and fine for a curated wiki. It's weak for fuzzy recall over a large corpus.

**What I'd do**

1. **Start with the format, not the server.** Create one `kb-<project>` repo as an OKF bundle with `services/`, `teams/<team>/` and a
   `decisions/` journal. Add a short `AGENTS.md` with the rules and link it from every code repo's `AGENTS.md`/`CLAUDE.md`. Run a
   lint in CI, either `carto`'s or a 50-line script. This costs a day and settles whether agents and people actually use the KB.
2. **Pilot Cartographer with two teams for two to four weeks** once more than a couple of people's agents are writing. Watch for refused
   writes (that's the guardrails working), conflicts, merge pain, and whether `cartographer sync` of skills saves real time.
3. **Decide on evidence.** If agents edit freely and quality holds, the plain bundle may be enough. If you see broken links,
   overwrites or nobody knowing where a claim came from, that's what Cartographer is for. Either way, nothing is wasted, because the files are the same.

Questions that would change this: How many people's agents would write, as opposed to read? Do you already run a docs portal such as
Backstage or Confluence that this must coexist with? Can your teams run a shared internal service, or must everything be local and git-only?
"""
