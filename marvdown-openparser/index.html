marvdown and openparser for nimib?

nimib turns Markdown into HTML with nim-markdown, reads nimib.toml with parsetoml and writes its blocks as JSON with jsony. George Lemon's marvdown (Markdown) and openparser (JSON, TOML and 28 other formats) could replace all three. This page measures what would change, from the simplest dependency to the hardest, and says who makes the new libraries and who uses them.

Version 2 · updated 28 Nov 2026

The short version
  • Fusion is used for one thing: captureStdout (src/nimib/capture.nim) calls duplicate and duplicateTo from fusion/ioutils, two wrappers of the C calls dup and dup2. About twenty lines of Nim replace it, and nimib loses a dependency.
  • TOML: openparser is better than parsetoml. On the official toml-test suite (TOML 1.0) it accepts all 208 valid files and rejects all 509 invalid ones; parsetoml accepts 184 of 208 and rejects 435 of 509. parsetoml had no commit in the last year.
  • JSON: no reason to move. jsony works, is maintained and used by 200+ packages; openparser can do the same job, but its hooks have another signature, so every block with a custom hook (and tabelline's book, which reads nimib's JSON) would have to change.
  • Markdown: marvdown is not ready. On CommonMark's 655 examples it gets 222 right (34%), nim-markdown 611 (93%). On 183 real Markdown files of the nimib repositories only 89 render the same. It drops lists that follow a paragraph and swallows the rest of a page after an inline <img>. It is 10 times faster and needs no PCRE.
  • The PCRE problem has a cheaper fix: port nim-markdown's 82 regular expressions to nim-regex (two use back references and need a few lines of code each), and fix the two inputs that crash it, found on the way.
  • Who uses them, how reliable: 43 repositories of the OpenPeeps family use openparser, two outside it (by Jaremy Creechley and David Krause); nobody outside uses marvdown yet. Both are well tested and very active, 0.x, and written by one person (George Lemon): a bus factor of one.

Fusion: one module, two C callsthe short answer to the second question↑ Contents

nimib imports fusion in exactly one place, src/nimib/capture.nim, for fusion/ioutils:

import fusion/ioutils   # duplicate, duplicateTo

captureStdout is how nbCode gets the output of its code: it copies the stdout file descriptor with duplicate, points stdout at a temporary file with duplicateTo, runs the code, reads the file and puts stdout back. duplicate is C's dup and duplicateTo is dup2 (_dup and _dup2 on Windows). The only other trace of fusion is withDir in paths.nim, already copied from fusion/scripting ("ported from fusion/scripting"), not imported.

So the whole dependency is two C calls. Here they are without fusion, run while this page was built (the block below runs inside nimib's own captureStdout, so it also checks that the two nest):

import std/tempfiles
when defined(windows):
  proc cDup(fd: cint): cint {.importc: "_dup", header: "<io.h>".}
  proc cDup2(fd, to: cint): cint {.importc: "_dup2", header: "<io.h>".}
else:
  proc cDup(fd: cint): cint {.importc: "dup", header: "<unistd.h>".}
  proc cDup2(fd, to: cint): cint {.importc: "dup2", header: "<unistd.h>".}

template captureStdoutNoFusion(ident: untyped, body: untyped) =
  let outFd = stdout.getFileHandle()
  let saved = cDup(outFd)                     # was fusion's duplicate
  let (tmp, path) = createTempFile("tmp", "")
  stdout.flushFile()
  doAssert cDup2(tmp.getFileHandle(), outFd) != -1   # was duplicateTo
  body
  stdout.flushFile()
  tmp.setFilePos(0)
  ident = tmp.readAll()
  tmp.close()
  removeFile(path)
  doAssert cDup2(saved, outFd) != -1

var captured: string
captureStdoutNoFusion(captured):
  echo "hello from inside"
echo "captured: ", captured.strip
captured: hello from inside
🐳 For nimib

Removing fusion is a small, safe change on its own: the template above, a test on Windows in CI, and one line less in nimib.nimble. It does not depend on anything else on this page.

What that means for nimib:

  • Well tested, very active. openparser has far more tests than anything nimib uses today, CI on every push and frequent releases. marvdown has tests and CI too, but its CommonMark tests pin the current output, divergences included (SPEC: comments), so they guard against change, not against wrong output: that is how "CommonMark compliant" and 34% fit together.
  • A bus factor of one. Both are written by one person, at a very high pace: OpenPeeps created 5 to 8 repositories a year from 2021 to 2025 and 35 in 2026; openparser is 47,000 lines in seven months, with a JIT regex engine, SIMD JSON, a QR reader and a NIF parser among its 30 modules. Speed is a strength while it lasts, and a risk if priorities move.
  • Young and still 0.x. 26 releases in 7 months means the API can move under nimib; pinning versions would be needed. Names and places have moved before, cleanly (the registry renamed bro to bowdy, and a batch of wrappers moved from openpeeps to nimbase: nim-lang/packages #3535 and #3546).
  • Its own tooling. The projects are developed with Clue, the family's alternative to nimble; they install with nimble too.
  • The old ones are not better maintained. nim-markdown and parsetoml are quiet, with no release in a year and no CI for nim-markdown. jsony is the healthy one. Moving would trade dormant dependencies for a live one with a single maintainer.

TOML: parsetoml or openparserthe simplest swap, and the clearest win↑ Contents

nimib reads one table of nimib.toml and keeps the rest of the text for others to read:

[nimib]
srcDir = "docsrc"
homeDir = "docs"

Today loadTomlSection parses the text with parsetoml, converts the section to JsonNode with 45 lines of customToJson, prints it and parses it again with jsony into the object. openparser parses TOML straight into an object, which removes those 45 lines and jsony from the config path:

import std/tables, openparser/toml
type Cfg = object
  nimib: NbConfig
let cfg = parseTOML(content, Cfg)    # unknown tables and keys are skipped by default

To compare the two parsers I ran the toml-test suite, the one TOML implementations use: a parser should accept every valid file and reject every invalid one.

Careful

One rough edge: parseTOML(text, T) did not compile until I added import std/tables to my own module (a generic in openparser calls pairs on an OrderedTableRef without binding it). Easy to work around, worth an issue upstream.

🐳 For nimib

For nimib.toml the gain is correctness on corner cases nimib users rarely write, and less code. The cost is the whole openparser package: 47,000 lines, Nim 2.2.10 or later, and nimble installs nimsimd, nimcypher and dynasm with it, even if only openparser/toml and openparser/json are compiled (json pulls nimsimd for its SIMD path).

JSON: jsony or openparsera sideways move with a breaking change↑ Contents

nimib uses JSON in three places: the config path above, the values that nbJsFromCode passes to the browser (toJson(x), parsed back with std/json), and its JSON backend: every block type registers a hook, so a document's seq[NbBlock] (of many subtypes) can be written to JSON and read back with the right types. tabelline's book uses that: it saves each chapter's blocks and renders them again later with readFile(path).fromJson(NbDoc).

jsony's hook gets the raw string and a position, parseHook(s: string, i: var int, v: var NbBlock); nimib reads the kind field, rewinds i and parses again as the right type. openparser's hook gets a parser object, parseHook(p: var JsonParser, v: var NbBlock), whose position is private, so it cannot rewind. It works with a detour through JsonNode, which I tried on a small block hierarchy (bench/tjson_op.nim):

proc parseHook(p: var JsonParser, v: var NbBlock) =
  var node: JsonNode
  parseHook(p, node)                       # parse the block once, as a tree
  v = registry[node["kind"].getStr](node)  # each kind: fromJson($node, ThatKind)

It wrote nested containers to JSON and read them back exactly (toJson(back) == s printed true), at the cost of parsing every block twice.

jsony to openparser/json
for openparserone JSON library for nimib and its TOML; SIMD parsing; {.json: "name".} field names (compile-time dump only, so far); depth limits
againstevery custom parseHook/dumpHook written for jsony breaks (new signature); nimib re-exports jsony, so pages that call toJson/fromJson through nimib change library; the JsonNode detour; nimibook keeps jsony anyway for book.json
speednot a factor: nimib writes a few kilobytes of JSON per page
🐳 For nimib

jsony is small (1,000 lines), maintained by treeform, named in 200+ nimble files and does the job. Swapping it only makes sense as part of adopting openparser for TOML, and even then nimib could keep jsony for blocks and use openparser only for the config.

The PCRE problem, and a cheaper fixwhy this came up, and what it would take↑ Contents

nim-markdown is built on std/re, which loads PCRE 1 (libpcre.so.3) at run time. Ubuntu 26.04 no longer ships it, so nimib's CI pins ubuntu-24.04 and installs libpcre3, and every sandbox that builds a nimib page needs the same trick. That is the real reason to look at marvdown: it needs no regular expressions from outside Nim.

But the cheaper fix is in nim-markdown itself. It has 82 regular expression literals, used through matchLen (54 times), replace, find, contains and match. nim-regex (pure Nim, by nitely, the engine behind Nim 2.4's std/nre2) handles lookahead (7 uses) and named groups (2), but not back references, which 2 patterns use (code spans: a run of backticks closed by the same run). Those two become a few lines of plain Nim each.

🐳 For nimib

Two API points make this manageable: markdownToHtml is the single place nimib renders Markdown, and loadTomlSection(content, section, T) the single place it reads TOML. Keep both signatures and most downstream code does not notice. The exceptions are the direct markdown(...) calls (nimiSlides, tabelline's book) and the jsony re-export.

Recommendation. Do the first two now: they remove what hurts (fusion, PCRE) without changing a single page. Keep jsony. Treat openparser's TOML as a good option for the next time nimib raises its minimum Nim, if openparser is still moving at the same quality and has gained users. Leave marvdown for later, and if its ideas appeal (anchors, front matter, the AST), the most useful thing nimib can do is send George Lemon this page's CommonMark runner: it turns "CommonMark compliant" into a number that can go up.

What would change my mind: marvdown passing 90% of the spec and rendering the nimib repositories' files like nim-markdown; openparser getting a second maintainer or wide use; nimib deciding to require Nim 2.2.10 anyway.

How this page is builtevery number is rerun by one script↑ Contents

The page is a nimib notebook (src/index.nim) with tables by tabelline; it reads every number from src/data/, which src/bench/run.sh writes:

  • bench/deps.sh fetches marvdown, openparser (and nimsimd, nimcypher, dynasm), nim-markdown, jsony, parsetoml and three test suites at pinned commits: commonmark-spec, cmark-gfm (the GFM extensions) and toml-test.
  • cm_*.nim and gfm_*.nim are four tiny programs, Markdown on stdin and HTML on stdout, one per library and setting. runspec.py feeds them every spec example and compares the HTML with CommonMark's own normalize.py (that is why it is Python: it reuses the official normalizer). realworld.py does the same for a folder of .md files.
  • tt_parsetoml.nim and tt_optoml.nim run toml-test's file lists; tjson_op.nim is the block round trip of the JSON chapter; bench.nim the speed table; cases.nim renders the cards of the Markdown chapter with both libraries in one program.
  • The dependents come from cloning (blob-less) every repository of George Lemon's organizations and reading their nimble files, then GitHub code search for the rest.

nbChapter("fusion", "Fusion: one module, two C calls", "the short answer to the second question")

nbText: &"""
nimib imports [fusion](https://github.com/nim-lang/fusion) in exactly one place,
[`src/nimib/capture.nim`]({nimibRepo}src/nimib/capture.nim), for `fusion/ioutils`:

```nim
import fusion/ioutils   # duplicate, duplicateTo
```

`captureStdout` is how `nbCode` gets the output of its code: it copies the stdout file
descriptor with `duplicate`, points stdout at a temporary file with `duplicateTo`, runs the code,
reads the file and puts stdout back. `duplicate` is C's `dup` and `duplicateTo` is `dup2`
(`_dup` and `_dup2` on Windows). The only other trace of fusion is `withDir` in `paths.nim`,
already copied from `fusion/scripting` ("ported from fusion/scripting"), not imported.

So the whole dependency is two C calls. Here they are without fusion, run while this page was built
(the block below runs inside nimib's own `captureStdout`, so it also checks that the two nest):
"""

nbCode:
  import std/tempfiles
  when defined(windows):
    proc cDup(fd: cint): cint {.importc: "_dup", header: "<io.h>".}
    proc cDup2(fd, to: cint): cint {.importc: "_dup2", header: "<io.h>".}
  else:
    proc cDup(fd: cint): cint {.importc: "dup", header: "<unistd.h>".}
    proc cDup2(fd, to: cint): cint {.importc: "dup2", header: "<unistd.h>".}

  template captureStdoutNoFusion(ident: untyped, body: untyped) =
    let outFd = stdout.getFileHandle()
    let saved = cDup(outFd)                     # was fusion's duplicate
    let (tmp, path) = createTempFile("tmp", "")
    stdout.flushFile()
    doAssert cDup2(tmp.getFileHandle(), outFd) != -1   # was duplicateTo
    body
    stdout.flushFile()
    tmp.setFilePos(0)
    ident = tmp.readAll()
    tmp.close()
    removeFile(path)
    doAssert cDup2(saved, outFd) != -1

  var captured: string
  captureStdoutNoFusion(captured):
    echo "hello from inside"
  echo "captured: ", captured.strip

nbText: &"""
nimib uses JSON in three places: the config path above, the values that `nbJsFromCode` passes
to the browser (`toJson(x)`, parsed back with `std/json`), and its **JSON backend**: every block
type registers a hook, so a document's `seq[NbBlock]` (of many subtypes) can be written to JSON
and read back with the right types. tabelline's book uses that: it saves each chapter's
blocks and renders them again later with `readFile(path).fromJson(NbDoc)`.

jsony's hook gets the raw string and a position, `parseHook(s: string, i: var int, v: var NbBlock)`;
nimib reads the `kind` field, rewinds `i` and parses again as the right type.
openparser's hook gets a parser object, `parseHook(p: var JsonParser, v: var NbBlock)`, whose
position is private, so it cannot rewind. It works with a detour through `JsonNode`, which I tried
on a small block hierarchy (`bench/tjson_op.nim`):

```nim
proc parseHook(p: var JsonParser, v: var NbBlock) =
  var node: JsonNode
  parseHook(p, node)                       # parse the block once, as a tree
  v = registry[node["kind"].getStr](node)  # each kind: fromJson($node, ThatKind)
```

`true`), at the cost of parsing every block twice.
