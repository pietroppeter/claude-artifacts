nimib on Nimony

nimib turns a Nim program into a web page: the text, the code and the code's output, like a notebook. Nimony is a new Nim compiler, the one meant to become Nim 3, built as a chain of tools that pass NIF files (a text format for code) to each other. Can a nimib page be compiled by Nimony? I tried, it can't, and so I wrote a small nimib that both compilers accept: this page is built with it, by Nimony. Then: would a nimib for both compilers be feasible, and a good idea?

Version 2

The short version
  • nimib does not compile with Nimony today, and neither does the Nimony explainer. The first error is an import cycle inside nimib; behind it are macros, missing stdlib modules and Nimony's stricter rules on exceptions and globals.
  • Patching does not get far. Fixing one nimib module by hand clears its first errors and shows the next ones. nimib's dependencies (nim-markdown, jsony, parsetoml, tabelline) stop too.
  • A small nimib for both compilers works. nimiboth is 580 lines of Nim (not counting its JS bindings): blocks, nbText, nbCode with its source and output, nbFile, custom blocks. Nim 2 and Nimony build the same test page byte for byte, and Nimony builds this page.
  • Nim in the page works too. nbJsFromCode compiles a block to JavaScript with the page's compiler; the demo is a NIF explorer of a small module at four stages of Nimony.
  • Feasible: yes for the core. The cost is everything around it: Markdown, JSON, TOML, Karax and the rest of nimib's JS family. Good idea: yes, in steps, starting with changes that also make nimib better on Nim 2, and not before Nimony's first stable release.

That is a port, module by module, through nimib and four libraries.

Why it breaksNim 2 and Nimony, side by side

None of this is a bug in Nimony. Its differences and porting guide say what changes, and nimib leans on almost all of it.

Macros

Nim 2

nimib reads the source of nbCode with a macro: lineInfoObj gives the lines, readFile gives the text. Blocks are declared with newNbBlock, a macro that uses getTypeFields, genAst and quote do. jsony builds its (de)serializers from getTypeImpl.

Nimony

Macros exist "for backwards compatibility" and run as separate programs. std/macros is small: no quote do, genAst, lineInfoObj, toStrLit, newLit or getTypeImpl. The new way is a plugin: a program that receives the call as a NIF tree, with line info, and returns a tree.

Exceptions

Nim 2

readFile raises IOError, and any proc may let it through. nimib does file I/O in many places without saying so.

Nimony

Errors are an ErrorCode. A proc that calls readFile must be marked .raises or catch it, and so must its callers. The canraise feature does not lift this.

Globals, tables, generics

Nim 2

Procs read the global nb; table[key] raises KeyError, which nobody checks; a parameter x: AnyPath makes a proc generic.

Nimony

A proc that reads a global var needs .sync (let is fine); table[key] is .raises, so it has the same problem as readFile; type-class parameters without [T] are not supported.

The standard library

Nim 2

nimib imports strformat, sugar, macrocache, jsonutils, cgi, browsers, the compiler's pathutils and highlite; nim-markdown needs re (PCRE) and htmlparser; tabelline uses staticRead.

Nimony

Nimony's stdlib is a rewrite: none of those modules are there, the os procs take a Path, not a string, and staticRead is spelled slurp. json, tables, strutils, os, osproc, unicode are there.

For Nim 2 users

Every one of these is also a page author's problem: a nimib page that uses &"..." in its nbText needs strformat, which Nimony does not have. Code inside nbCode is compiled by the compiler you choose, so it has to be Nimony code.

A minimal nimib for both compilersnimiboth, the library this page uses

So instead of porting nimib I wrote the smallest thing that still is nimib, in the part of the language both compilers agree on: nimiboth. It keeps nimib 0.4's design, a document as a list of blocks with one render proc per kind, and these blocks: nbText (Markdown), nbCode, nbCodeSkip, nbFile, nbRawHtml, and custom blocks like the ones on this page.

The one real difference is how nbCode gets its source. In Nim 2 it is a macro, as in nimib. In Nimony it is a template plugin: template codeSource(body: untyped): string {.plugin: "plugins/codesource".}. The compiler builds the plugin, hands it the block as a NIF tree, and the plugin finds the first and last line in the tree's line info, reads them from the file and returns them as a string literal. The plugin is in the sources at the end.

Careful

nimiboth is an experiment, not nimib. Its JS support is one block, nbJsFromCode (one program per block, see the NIF explorer); there is no nbJsFromCodeInBlock, no Karax, no sharing code between JS blocks. It has no nimib.toml, no Markdown or JSON backend, no nbImage path rewriting, and its Markdown is a subset (headings, paragraphs, lists, quotes, fences, code, bold, italic, links; no tables or HTML: the tables on this page are a custom block). Its capture uses POSIX dup2, so it is Linux and macOS only.

What a nimib for both could look likea design, from what broke

nimiboth suggests a shape: a small core that both compilers accept, and everything else on top.

  1. A portable core (nimib/core): the document, blocks as plain ref objects with a render proc each, nbText, nbCode, nbFile, nbJsFromCode, rendering to HTML, stdout capture. No macros, no strformat, no global var read by procs, I/O through a few procs that catch errors.
  2. One shim module per compiler difference, as nimiboth/shim.nim: source capture (macro or plugin), C strings, file I/O. Nimony's std/macros keeps growing, so the shim can shrink.
  3. Swappable Markdown. nim-markdown is the biggest dependency that does not compile. Either port it off re and htmlparser, or keep a small renderer in the core and use nim-markdown on Nim 2 when it is there.
  4. Nim 2 extras stay where they are: jsony and the JSON backend, nimib.toml with parsetoml, Karax and HappyX blocks, the newNbBlock macro as sugar over plain blocks. nbJsFromCode itself can be in the core: nimiboth compiles it with nimony j or nim js, whichever builds the page, and a few DOM bindings cover both (the NIF explorer).
  5. A Nimony canary in CI: build one core-only example with the Nimony nightly, so breakage shows the day it happens.

Something JS: a NIF explorernbJsFromCode, compiled by the page's compiler

nimib can run Nim in the page: nbJsFromCode compiles a block to JavaScript. nimiboth has it too. The block's source comes from the same plugin (or macro) as nbCode; nimiboth writes it to a file after import jsdom, a dozen DOM bindings that both JS back ends accept, and compiles it with the compiler that builds the page: nimony j --browser under Nimony (its JavaScript back end, jorogumo), nim js under Nim 2. The JavaScript goes into the page inline.

How to read it:

  • A node is (tag child child …), and the explorer shows the file exactly as Nimony wrote it. Tap the arrow before a ( to fold a node to (tag … n), where n counts its children; nodes deeper than three levels start folded, as in a code editor.
  • . is an empty slot (a proc with no pragmas has . where the pragmas go).
  • @… after a node is where it came from in the source: column, line and file, written relative to the node around it to keep files small.
  • name.0. is a symbol: a name the compiler has resolved, with a number that tells it apart from other things with the same name.

What each stage is, and what to look for:

  • parsed (nifler, .p.nif): the syntax only. square is just a name.
  • checked (nimsem, .s.nif): names resolved and types known. square is the symbol square.0., its type is (i 64), and 1 .. 3 is a call of the .. iterator.
  • lowered (shoggoth, .x.nif): the for loop is gone, its iterator inlined into a loop, and a dce node lists what the module uses, for dead-code elimination.
  • Leng (.c.nif): the low-level IR the C and native back ends read. There is now a main proc with argc and argv, ready for C.

The explorer parses NIF itself, in about 60 lines (in its code above, folded): the compiler's own NIF reader uses memory-mapped files and does not compile to JavaScript.

Careful

What I saw, building this: Nimony's browser programs end by throwing nim_exit(0), which nimiboth catches; a callback that touches a global needs {.cast(assumeSync).} (jsdom's sync); there is no std/dom, so the bindings are a handful of {.importjs.} procs. And size: the explorer is 312 KB of JavaScript from Nimony, 34 KB from Nim 2. Nimony's JS back end shares its code generator with the WebAssembly one and keeps Nim's data in one linear memory buffer (its design notes), with its runtime in the file; Nim 2 maps Nim's types to JavaScript's own.

Is it feasible? Is it a good idea?my answer, and what it rests on

Feasible?

Yes for the core, and this page shows it: one source builds the core with both compilers, with one shim module and one small plugin. The ecosystem is the real cost: Markdown, JSON serialization, TOML config, highlighting and the JS blocks beyond the simplest one (Karax, shared code between blocks) are each a port or a rewrite, and every library a page uses (tabelline here) must compile with Nimony too.

A good idea?

Yes, in steps, and not all at once. For it: nimib would be ready when people start writing Nim 3, Nimony itself could document its stdlib with literate pages, and the core gets simpler on Nim 2 too. Against it: Nimony is a moving target (this experiment ran on a commit from the same evening), every feature would be tested on two compilers, and the macro-based conveniences (newNbBlock, & in nbText) are what users like about nimib.

What I would do: the small changes above now, a portable core after Nimony's first stable release, and no fork. A when defined(nimony) in every module would be the wrong way.

Aside

Speed, measured once on the machine that built this page: Nimony builds it from scratch in about 5 seconds (each plugin is a program it compiles first) and again after an edit in half a second; Nim 2 takes about a second and a half. And the two builds of this page, leaving out the compiled JavaScript, differ in 2 lines of HTML: the ones that print the compiler's name.

""", """

nbPair("""

""", """

""")

nbChapter("evolution", "What a nimib for both could look like", "a design, from what broke")

nbText """
nimiboth suggests a shape: a small core that both compilers accept, and everything else on top.

1. **A portable core** (`nimib/core`): the document, blocks as plain `ref object`s with a render
   proc each, `nbText`, `nbCode`, `nbFile`, `nbJsFromCode`, rendering to HTML, stdout capture. No macros, no

2. **One shim module** per compiler difference, as `nimiboth/shim.nim`: source capture (macro or
   plugin), C strings, file I/O. Nimony's `std/macros` keeps growing, so the shim can shrink.
3. **Swappable Markdown.** nim-markdown is the biggest dependency that does not compile. Either
   port it off `re` and `htmlparser`, or keep a small renderer in the core and use nim-markdown
   on Nim 2 when it is there.
4. **Nim 2 extras stay where they are:** jsony and the JSON backend, `nimib.toml` with
   parsetoml, Karax and HappyX blocks, the `newNbBlock` macro as sugar over plain blocks.
   `nbJsFromCode` itself can be in the core: nimiboth compiles it with `nimony j` or `nim js`,
   whichever builds the page, and a few DOM bindings cover both (the [NIF explorer](#nif)).
5. **A Nimony canary in CI:** build one core-only example with the Nimony nightly, so breakage
   shows the day it happens.
"""

How to read it:

- A node is `(tag child child …)`, and the explorer shows the file exactly as Nimony wrote it.
  Tap the arrow before a `(` to fold a node to `(tag … n)`, where n counts its children; nodes
  deeper than three levels start folded, as in a code editor.

- `@…` after a node is where it came from in the source: column, line and file, written relative

- `name.0.` is a symbol: a name the compiler has resolved, with a number that tells it apart
  from other things with the same name.

What each stage is, and what to look for:

- **parsed** (*nifler*, `.p.nif`): the syntax only. `square` is just a name.
- **checked** (*nimsem*, `.s.nif`): names resolved and types known. `square` is the symbol

  and a `dce` node lists what the module uses, for dead-code elimination.

  proc with `argc` and `argv`, ready for C.

nbJsFromCode("nifx"):
  const stages = [("p", "parsed", "nifler: the syntax tree, .p.nif"),
                  ("s", "checked", "nimsem: types and symbols resolved, .s.nif"),
                  ("x", "lowered", "shoggoth: iterators inlined, dead code marked, .x.nif"),
                  ("c", "Leng", "the low-level IR the C and native back ends read, .c.nif")]
  const blank = {' ', '\n', '\r', '\t'}

  proc esc(s: string): string =
    result = ""
    for c in s:
      case c
      of '&': result.add "&amp;"
      of '<': result.add "&lt;"
      of '>': result.add "&gt;"
      else: result.add c

  proc splitInfo(tok: string): (string, string) =
    ## `call@6,9` -> ("call", "@6,9"): the token, and its line info
    var inStr = false
    for i in 0 ..< tok.len:
      if tok[i] == '"': inStr = not inStr
      elif tok[i] == '@' and not inStr and i > 0: return (tok.substr(0, i - 1), tok.substr(i))
    result = (tok, "")

  proc colour(tok, tagClass: string): string =
    ## a token with its line info, in the colours of its kind
    let (text, info) = splitInfo(tok)
    let cls = if tagClass.len > 0: tagClass
              elif text.len > 0 and text[0] == '"': "s"
              elif text.len > 0 and text[0] in {'0'..'9', '-'}: "n"
              elif text == ".": "e"
              elif '.' in text: "y"
              else: "i"
    result = "<span class=\"" & cls & "\">" & esc(text) & "</span>"
    if info.len > 0: result.add "<span class=\"li\">" & esc(info) & "</span>"

  proc node(src: string; i: var int; depth: int; count: var int): string =
    ## the node at `src[i]`, as the NIF text it is, with its spacing kept; a node over several
    ## lines gets a fold button and starts folded from depth 3
    if src[i] != '(':
      var tok = ""
      var inStr = false
      while i < src.len and (inStr or src[i] notin blank + {'(', ')'}):
        if src[i] == '"': inStr = not inStr
        tok.add src[i]
        inc i
      return colour(tok, "")
    inc i
    var tag = ""
    while i < src.len and src[i] notin blank + {'(', ')'}:
      tag.add src[i]
      inc i
    inc count
    var kids = ""
    var n = 0
    while i < src.len and src[i] != ')':
      if src[i] in blank:
        kids.add src[i]
        inc i
      else:
        kids.add node(src, i, depth + 1, count)
        inc n
    if i < src.len: inc i   # the `)`
    let head = "<span class=\"p\">(</span>" & colour(tag, if tag.len > 0 and tag[0] == '.': "d" else: "t")
    if '\n' notin kids:   # a node on one line is not folded, as in a code editor
      return head & kids & "<span class=\"p\">)</span>"
    result = "<span class=\"nd" & (if depth >= 3: " c" else: "") & "\"><button class=\"fold\" type=\"button\"" &
      " aria-label=\"fold\"></button>" & head & "<span class=\"kids\">" & kids &
      "</span><span class=\"dots\"> … " & $n & "</span><span class=\"p\">)</span></span>"

  proc show(st: string) =
    let src = toNim(textContent(byId(toJs("nif-" & st))))
    var i = 0
    var count = 0
    var html = ""
    while i < src.len:
      if src[i] in blank:
        html.add src[i]
        inc i
      else:
        html.add node(src, i, 0, count)
    var what = ""
    for s in stages:
      if s[0] == st: what = s[2]
    setHtml(byId("nifx-what"), toJs(esc(what) & " · " & $count & " nodes · " & $src.len & " bytes"))
    setHtml(byId("nifx-code"), toJs(html))
    removeAll(".nifx-tabs button", "aria-pressed")
    setAttr(byId(toJs("nifx-" & st)), "aria-pressed", "true")

  proc showP() = show("p")
  proc showS() = show("s")
  proc showX() = show("x")
  proc showC() = show("c")
  proc openAll() = removeClassAll("#nifx-code .nd", "c")
  proc foldAll() = addClassAll("#nifx-code .nd .nd", "c")

  var ui = "<div class=\"nifx-tabs\" role=\"group\" aria-label=\"stage\">"
  for s in stages:
    ui.add "<button id=\"nifx-" & s[0] & "\" type=\"button\">" & s[1] & "</button>"
  ui.add "</div><div class=\"nifx-file\"><div class=\"nifx-bar\"><span id=\"nifx-what\"></span>" &
    "<span class=\"nifx-acts\"><button id=\"nifx-open\" type=\"button\">open all</button>" &
    "<button id=\"nifx-fold\" type=\"button\">fold all</button></span></div>" &
    "<pre><code id=\"nifx-code\"></code></pre></div>"
  setHtml(byId("nifx"), toJs(ui))
  onClick(byId("nifx-p"), showP)
  onClick(byId("nifx-s"), showS)
  onClick(byId("nifx-x"), showX)
  onClick(byId("nifx-c"), showC)
  onClick(byId("nifx-open"), openAll)
  onClick(byId("nifx-fold"), foldAll)
  toggleParentOnClick(byId("nifx-code"), ".fold", "c")
  show("p")
