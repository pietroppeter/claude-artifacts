Decoding base64 email attachments, now with Nim

Daniel Lemire ranked programming languages by how fast their standard base64 decoder reads an email attachment, line breaks included. We ran his benchmark again and added Nim: the standard library, a faster plain-Nim decoder, two SIMD decoders written in Nim, and Nim calling simdutf. The question

The post (20 November 2026) makes one megabyte of random bytes, encodes it as base64 with 76-character lines ending in CRLF (1.37 MB of text, as in an email), and times the standard decoder of each language. The point: many fast decoders only work on base64 without line breaks, and fall back to a slow path at the first CRLF. simdutf removes line endings inside its vector loop, so everything built on it (C++, Node.js, Bun, Deno, PHP with his pull request, Python's fastpybase64) sits at the top, and the rest sits 10 to 30 times lower.

We used his code unchanged (same input generator, same protocol: check the bytes, warm up 600 calls, keep the best of 10 batches of 200 calls, median of runs) and wrote a Nim harness that follows the same protocol.

The Nim decoders

The three decoders we wrote end the same way: decodeTail in b64scalar.nim handles the last few characters and the = padding, character by character. They differ in the hot loop. Every one is checked on the benchmark input (length and byte sum, as in the other languages) and in bench/nim/test.nim against std/base64 on random inputs of every size from 0 to 3,000 bytes, with CRLF, LF, space and no line breaks, and with one corrupted character that must raise. Result: ok: 15005 round trips x 4 decoders, 14970 corrupted inputs rejected x 3 decoders.

1. std/base64: 1.0 GB/s

The standard library already copes with line breaks: before each group of four characters it skips \r, \n and spaces. Each character is then a table lookup, a check and a shift, written one byte at a time. That is about Go's speed (1.4 GB/s) and Java's (1.0 GB/s), faster than Zig's decoderWithIgnore (0.7 GB/s), and twice stock PHP (0.5 GB/s).

2. Plain Nim, four tables: 4.0 GB/s

Base64 packs 3 bytes (24 bits) into 4 characters of 6 bits each. A plain decoder (like std/base64) looks up each character's 6-bit value, checks it, then shifts and ORs the four values together and writes three bytes one by one.

The trick comes from modp_b64, the base64 code of Nick Galbreath's stringencoders C library, which Chromium has long shipped as third_party/modp_b64 for its own base64 functions. It moves the shifting into the tables: instead of one table of 6-bit values, four tables d0..d3, one per position in the group of four. d0[c] holds the value of c already shifted to bits 23..18, d1[c] to bits 17..12, and so on, and already in the byte order the CPU stores (little-endian). Decoding a group is then four loads and three ORs, and one 4-byte store writes the three bytes (the fourth byte is overwritten by the next group). An invalid character's entry has bits above the 24 set, so one comparison of the result checks all four characters. With "TWFu", the base64 of "Man":

A line ending is skipped when it starts a group, which it always does with 76-character lines (76 is a multiple of 4). Anywhere else it sends the decoder to the slow path in decodeTail for the rest of the input, the cliff Lemire's post is about: this decoder is fast for email and PEM (64 is a multiple of 4 too), not for any line length.

3. AVX2 with nimsimd: 6.3 GB/s

nimsimd gives Nim the x86 intrinsics up to AVX2. The decoder works on a 4 KB buffer in two steps:

  1. compact: copy the input 32 bytes at a time. A block with no byte at or below 0x20 is one load and one store. A block with a line ending is compacted 8 bytes at a time with BMI2 pext, which keeps the bytes a mask selects.
  2. decode: the Muła–Lemire AVX2 algorithm: three pshufb lookups validate and translate 32 characters, two multiply-adds and two shuffles pack them into 24 bytes.
bench/nim/b64avx2.nim lines 69–94
while b < BufSize and i + 32 <= m:
  let x = ld(src[i].addr)
  let mask = cast[uint32](mm256_movemask_epi8(
    mm256_cmpeq_epi8(mm256_max_epu8(x, space), space)))  # bytes <= 0x20
  # only \r \n space tab may be dropped; anything else <= 0x20 is an error
  let exact = cast[uint32](mm256_movemask_epi8(mm256_or_si256(
    mm256_or_si256(mm256_cmpeq_epi8(x, cr), mm256_cmpeq_epi8(x, lf)),
    mm256_or_si256(mm256_cmpeq_epi8(x, space), mm256_cmpeq_epi8(x, tab)))))
  bad = bad or (exact xor mask)
  # A clean block is one 32-byte store. Otherwise drop the marked bytes
  # 8 at a time with BMI2 pext. (A branch-free version that always takes
  # the pext path measured slower: about 5.5 vs 6.7 GB/s.)
  if mask == 0:
    mm256_storeu_si256(buf[b].addr, x)
    b += 32
  else:
    for g in 0..3:
      let m8 = (mask shr (8*g)) and 0xFF
      var w: uint64
      copyMem(w.addr, src[i + 8*g].addr, 8)
      w = pext_u64(w, not expand[m8])
      # a plain 8-byte store (copyMem here became a _FORTIFY_SOURCE
      # __memcpy_chk call on Ubuntu's gcc)
      cast[ptr uint64](buf[b].addr)[] = w
      b += 8 - mm_popcnt_u32(m8).int  # (std/bitops countSetBits compiled to a call here)
  i += 32

On the same machine it decodes base64 without line breaks at about 10 GB/s, so the compaction step costs about a third.

4. AVX-512 VBMI2: 11.4 GB/s

nimsimd stops at AVX2, so b64avx512.nim imports the dozen AVX-512 intrinsics it needs with importc. Same two steps, 64 bytes at a time, and both get simpler: vpcompressb drops the line endings of a 64-byte block in one instruction (no branch at all), and one vpermi2b translates 64 characters through a 128-entry table, as in Muła and Lemire's AVX-512 decoder. That is roughly what simdutf does on this CPU (its "icelake" kernel); part of the gap left (11.4 vs 14.4 GB/s) is probably that simdutf, as the post says, decodes clean blocks straight from the input and compacts only the blocks that need it.

5. Nim calling simdutf: 14.2 GB/s

The same as PHP's pull request or Python's fastpybase64: Nim calls the C++ library. Nim compiles to C here (the C backend, not nim cpp), and C cannot call a C++ function directly, so simdutf_wrap.cpp is a small extern "C" wrapper around simdutf::base64_to_binary. g++ compiles it and simdutf into object files, simdutf.nim declares the wrapper's functions with {.importc.} and links the objects with -lstdc++. With nim cpp one could instead call simdutf directly with {.importcpp.} and no wrapper; it would run the same simdutf code.

C++, Python and Nim all run the same simdutf kernel ("icelake", the AVX-512 one), so they should be equally fast, and they are, within this machine's noise: 14.4, 15.2 and 14.2 GB/s. Calling through Python or Nim adds a few nanoseconds per call, nothing next to the 94 µs a call takes to decode 1.37 MB. The compiler is not it either: the C++ benchmark built with clang 18 instead of g++ 13 ran at the same speed (14.0 to 14.7 GB/s in three runs); the fastpybase64 wheel was built with clang 21.

What we found

Three things cost more than the algorithm while writing the AVX2 decoder, each found by reading the generated assembly:

  • countSetBits from std/bitops showed up as a function call in the hot loop, where one popcnt instruction was wanted. mm_popcnt_u32 from nimsimd is the instruction.
  • copyMem into a stack array became __memcpy_chk, because Ubuntu's gcc turns on _FORTIFY_SOURCE. Each call also emitted a vzeroupper. A plain 8-byte store through a ptr uint64 took the AVX2 decoder from 1.6 to 5.5 GB/s.
  • A branch-free compaction was slower (5.5 GB/s) than branching on "is this block clean?" (6.7 GB/s): with 78-byte lines more than half of the 32-byte blocks are clean, and the predictor copes.
For Nim

The cheap win is the scalar decoder: plain Nim, no SIMD, no new dependency, and 4.0x faster than std/base64 on email attachments. It could go to the standard library as it is (with decode keeping its signature). The SIMD decoders need a CPU check at run time (nimsimd's runtimecheck) before they could be used anywhere but on a machine you know.

## Fast scalar MIME base64 decoder in plain Nim.
##
## Four 256-entry uint32 tables (the modp_b64 / Chromium trick) turn four
## characters into three bytes with four loads and three ORs. A bad character
## sets the top bit, so one comparison per quad validates it. Line endings
## (and spaces) are skipped wherever they occur.

const bad* = 0x01FF_FFFF'u32   ## any table entry >= bad marks an invalid character

func charValue(c: char): int =
  case c
  of 'A'..'Z': ord(c) - ord('A')
  of 'a'..'z': ord(c) - ord('a') + 26
  of '0'..'9': ord(c) - ord('0') + 52
  of '+': 62
  of '/': 63
  else: -1

func makeTable(shift: int): array[256, uint32] =
  # Output bytes are stored little-endian: byte0 | byte1 << 8 | byte2 << 16.
  for i in 0..255:
    let v = charValue(char(i))
    if v < 0:
      result[i] = bad
    else:
      # 24-bit big-endian value (v << shift), then byte-swapped into place.
      let x = uint32(v) shl shift
      result[i] = ((x shr 16) and 0xFF) or (x and 0xFF00) or ((x and 0xFF) shl 16)

const
  d0* = makeTable(18)   ## first character of a group: bits 23..18 of the 24
  d1* = makeTable(12)
  d2* = makeTable(6)
  d3* = makeTable(0)    ## fourth character: bits 5..0

template isSpace(c: char): bool = c in {'\r', '\n', ' ', '\t'}

proc decodeError(i: int) {.noinline, noreturn.} =
  raise newException(ValueError, "invalid base64 character at " & $i)

func maxDecodedLen*(n: int): int = (n div 4) * 3 + 3

proc decodeTail*(src: ptr UncheckedArray[char], i0, n: int,
                 dst: ptr UncheckedArray[char], o0: int): int =
  ## Slow path: skips spaces character by character, handles padding.
  ## Returns the new output index.
  var acc = 0'u32
  var k = 0
  var o = o0
  var i = i0
  while i < n:
    let c = src[i]
    inc i
    if isSpace(c): continue
    if c == '=':   # padding: only more '=' and spaces may follow
      while i < n:
        if src[i] != '=' and not isSpace(src[i]): decodeError(i)
        inc i
      break
    let v = charValue(c)
    if v < 0: decodeError(i - 1)
    acc = (acc shl 6) or uint32(v)
    inc k
    if k == 4:
      dst[o] = char((acc shr 16) and 0xFF); dst[o+1] = char((acc shr 8) and 0xFF); dst[o+2] = char(acc and 0xFF)
      o += 3; k = 0; acc = 0
  case k
  of 0: discard
  of 2:
    dst[o] = char((acc shr 4) and 0xFF); o += 1
  of 3:
    dst[o] = char((acc shr 10) and 0xFF); dst[o+1] = char((acc shr 2) and 0xFF); o += 2
  else: decodeError(i)
  o

proc decodeScalar*(src: ptr UncheckedArray[char], n: int,
                   dst: ptr UncheckedArray[char]): int =
  ## Decodes `n` characters of (line-broken) base64 at `src` into `dst`,
  ## which needs `maxDecodedLen(n) + 1` bytes. Returns the decoded length.
  var i = 0
  var o = 0
  # Fast loop: whole quads with no space inside. 4-byte stores (3 valid).
  while i + 4 < n:
    let c0 = src[i]
    if isSpace(c0):
      inc i
      continue
    let x = d0[uint8 c0] or d1[uint8 src[i+1]] or d2[uint8 src[i+2]] or d3[uint8 src[i+3]]
    if x >= bad: break   # a space inside the quad, padding or a bad char
    copyMem(addr dst[o], unsafeAddr x, 4)
    i += 4
    o += 3
  decodeTail(src, i, n, dst, o)

proc decodeScalar*(s: string): string =
  result = newStringUninit(maxDecodedLen(s.len) + 1)
  let n = decodeScalar(cast[ptr UncheckedArray[char]](s.cstring), s.len,
                       cast[ptr UncheckedArray[char]](result.cstring))
  result.setLen(n)

        hiNib = mm256_and_si256(mm256_srli_epi32(v, 4), mask2F)
        loNib = mm256_and_si256(v, mask2F)
        lo = mm256_shuffle_epi8(lutLo, loNib)
        hi = mm256_shuffle_epi8(lutHi, hiNib)
        eq2F = mm256_cmpeq_epi8(v, mask2F)
        roll = mm256_shuffle_epi8(lutRoll, mm256_add_epi8(eq2F, hiNib))
      if mm256_testz_si256(lo, hi) == 0: decodeError(i)
      v = mm256_add_epi8(v, roll)
      var w = mm256_madd_epi16(mm256_maddubs_epi16(v, k1), k2)
      w = mm256_permutevar8x32_epi32(mm256_shuffle_epi8(w, pack), perm)
      mm256_storeu_si256(dst[o].addr, w)   # 24 useful bytes
      j += 32; o += 24
    if j < b: moveMem(buf[0].addr, buf[j].addr, b - j)
    b -= j
    if i + 32 > m: break

  const alphabet = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/"
  var t: array[128, int8]

    result[1][i] = t[i + 64]

                   dst: ptr UncheckedArray[char]): int =
  ## `dst` needs `maxDecodedLen(n) + 64` bytes. Returns the decoded length.
  let
    lut0 = mm512_loadu_si512(lut0A.unsafeAddr)
    lut1 = mm512_loadu_si512(lut1A.unsafeAddr)
    pack = mm512_loadu_si512(packA.unsafeAddr)
    space = mm512_set1_epi8(0x20)
    cr = mm512_set1_epi8(0x0D)
    lf = mm512_set1_epi8(0x0A)
    tab = mm512_set1_epi8(0x09)
    k1 = mm512_set1_epi32(0x01400140'i32)
    k2 = mm512_set1_epi32(0x00011000'i32)

  while m > 0 and src[m-1] in {'\r', '\n', ' ', '\t', '='}: dec m
  var buf {.noinit.}: array[BufSize + 128, char]
  var i, o, b = 0

    var bad = 0'u64
    while b < BufSize and i + 64 <= m:
      let x = mm512_loadu_si512(src[i].addr)
      let ws = mm512_cmple_epu8_mask(x, space)
      let exact = mm512_cmpeq_epi8_mask(x, cr) or mm512_cmpeq_epi8_mask(x, lf) or
                  mm512_cmpeq_epi8_mask(x, space) or mm512_cmpeq_epi8_mask(x, tab)
      bad = bad or (ws xor exact)
      mm512_storeu_si512(buf[b].addr, mm512_maskz_compress_epi8(not ws, x))
      b += 64 - int(mm_popcnt_u64(ws))
      i += 64
    if bad != 0: decodeError(i)
    var j = 0
    while j + 64 <= b:
      let v = mm512_loadu_si512(buf[j].addr)
      let t = mm512_permutex2var_epi8(lut0, v, lut1)
      if mm512_movepi8_mask(mm512_or_si512(t, v)) != 0: decodeError(i)
      let w = mm512_madd_epi16(mm512_maddubs_epi16(t, k1), k2)
      mm512_storeu_si512(dst[o].addr, mm512_permutexvar_epi8(pack, w))  # 48 useful bytes
      j += 64; o += 48

### 2. Plain Nim, four tables: {g(nimScalar)} GB/s

import std/[re, algorithm, strutils, tables, os, sequtils]

type Speed* = object
  system*, function*: string
  runs*: seq[float]
  median*: float

func median(v: seq[float]): float =
  let s = v.sorted
  if s.len mod 2 == 1: s[s.len div 2] else: (s[s.len div 2 - 1] + s[s.len div 2]) / 2

proc readRuns*(dir, prefix: string): seq[Speed] =
  ## All `<prefix>*.txt` files in `dir`, one row per (system, function), fastest first.
  let lineRe = re"^(.*?) mime (.*): ([0-9.]+) GB/s$"
  var speeds = initOrderedTable[(string, string), seq[float]]()
  for path in toSeq(walkFiles(dir / prefix & "*.txt")).sorted:
    for line in lines(path):
      var m: array[3, string]
      if line.strip.match(lineRe, m):
        speeds.mgetOrPut((m[0], m[1]), @[]).add parseFloat(m[2])
  for k, v in speeds:
    result.add Speed(system: k[0], function: k[1], runs: v, median: median(v))
  result.sort(proc(a, b: Speed): int = cmp(b.median, a.median))

proc header*(dir, file: string): seq[string] =
  ## The first lines of a results file: kernel, CPU, compiler.
  for line in lines(dir / file):
    if " mime " in line: break
    result.add line

func isNim*(r: Speed): bool = r.system.startsWith("nim ")

proc pick*(rows: seq[Speed], system, function: string): Speed =
  ## The row whose system starts with `system` and whose function contains `function`.

Base64 packs 3 bytes (24 bits) into 4 characters of 6 bits each. A plain decoder (like

(the fourth byte is overwritten by the next group). An invalid character's entry has bits above

   one load and one store. A block with a line ending is compacted 8 bytes at a time with
   BMI2 `pext`, which keeps the bytes a mask selects.
2. **decode**: the Muła–Lemire AVX2 algorithm: three `pshufb` lookups validate and translate
   32 characters, two multiply-adds and two shuffles pack them into 24 bytes.

"""

nbFile "bench/nim/b64avx2.nim", start = "while b < BufSize and i + 32", stop = "if bad != 0"

nbText: &"""

On the same machine it decodes base64 without line breaks at about 10 GB/s, so the
compaction step costs about a third.

### 4. AVX-512 VBMI2: {g(nimAvx512)} GB/s

nimsimd stops at AVX2, so `b64avx512.nim` imports the dozen AVX-512 intrinsics it needs
with `importc`. Same two steps, 64 bytes at a time, and both get simpler:
`vpcompressb` drops the line endings of a 64-byte block in one instruction (no branch at all),
and one `vpermi2b` translates 64 characters through a 128-entry table, as in Muła and Lemire's
AVX-512 decoder. That is roughly what simdutf does on this CPU (its "icelake" kernel); part of
the gap left ({g(nimAvx512)} vs {g(cpp)} GB/s) is probably that simdutf, as the post says, decodes
clean blocks straight from the input and compacts only the blocks that need it.

"""

nbFile "bench/nim/b64avx512.nim", start = "while b < BufSize and i + 64", stop = "if bad != 0"

nbText: &"""

### 5. Nim calling simdutf: {g(nimFfi)} GB/s

The same as PHP's pull request or Python's fastpybase64: Nim calls the C++ library. Nim
compiles to C here (the C backend, not `nim cpp`), and C cannot call a C++ function directly, so
`simdutf_wrap.cpp` is a small `extern "C"` wrapper around `simdutf::base64_to_binary`. g++
compiles it and simdutf into object files, `simdutf.nim` declares the wrapper's functions with
`{{.importc.}}` and links the objects with `-lstdc++`. With `nim cpp` one could instead call
simdutf directly with `{{.importcpp.}}` and no wrapper; it would run the same simdutf code.

C++, Python and Nim all run the same simdutf kernel ("icelake", the AVX-512 one), so they should
be equally fast, and they are, within this machine's noise: {g(cpp)}, {g(ours.pick("python", "fastpybase64"))}
and {g(nimFfi)} GB/s. Calling through Python or Nim adds a few nanoseconds per call, nothing
next to the {int(1368424.0 / cpp.median / 1000)} µs a call takes to decode
1.37 MB. The compiler is not it either: the C++ benchmark built with clang 18 instead of g++ 13
ran at the same speed (14.0 to 14.7 GB/s in three runs); the fastpybase64 wheel was built with clang 21.
"""

nbNote(nkReading, """
Three things cost more than the algorithm while writing the AVX2 decoder, each found by reading
the generated assembly:

- **`countSetBits` from `std/bitops`** showed up as a function call in the hot loop, where one
  `popcnt` instruction was wanted. `mm_popcnt_u32` from nimsimd is the instruction.
- **`copyMem` into a stack array** became `__memcpy_chk`, because Ubuntu's gcc turns on
  `_FORTIFY_SOURCE`. Each call also emitted a `vzeroupper`. A plain 8-byte store through a
  `ptr uint64` took the AVX2 decoder from 1.6 to 5.5 GB/s.
- **A branch-free compaction was slower** (5.5 GB/s) than branching on "is this block clean?"
  (6.7 GB/s): with 78-byte lines more than half of the 32-byte blocks are clean, and the predictor copes.
""")
