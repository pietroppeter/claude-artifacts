🏡 Nimony, explained: how Nim 3's compiler grew up

Nimony, explained

Nimony is Andreas Rumpf's (Araq's) new Nim compiler, the one meant to become Nim 3. For two years he has posted its progress on the Nim forum one line at a time: "NJVL", "Shoggoth", "Arkham", "BIF", "avoidtemps". This is the story told in order, from the forum threads, the nimony repo (2,348 commits) and Araq's blog, with every term explained at the point where it shows up.

Version 1 · updated 22 Nov 2026

The short version
  • What it is. A from-scratch Nim compiler built as a chain of small tools that pass NIF files to each other (NIF is a Lisp-like text format, "JSON for compilers"). Because every step reads and writes files, incremental and parallel builds come almost for free.
  • Why. After twenty years the old compiler could not get incremental compilation, type-checked generics or a clean phase order. Araq: "I don't know how to bring all this good stuff into Nim's old codebase without going insane."
  • How it went. First "hello world" on 22 Feb 2025; a minimal language ("aufbruch") by May 2025; release 0.2 in Nov 2025; it compiled itself in Apr 2026; its own native backend (Arkham, no C compiler) bootstrapped in Aug 2026; Araq calls it feature complete in Oct 2026 and a "great christmas release" is planned.
  • Side effect. The ideas flowed back: Nim 2.4 (28 Oct 2026) ships incremental compilation built the Nimony way. Nim 2.x and Nimony now "compete for the Nim 3 title".
  • avoidtemps (your example) is a type plugin: mark a type with it and the compiler rewrites let e = a*b + c - d into var e = a; e *= b; e += c; e -= d, so no temporary values are created. Promised in May 2025, shipped today, 22 Nov 2026.

Start with your example: avoidtempspromised 3 May 2025, shipped 22 Nov 2026

Take a small matrix type with the usual operators. Each operator copies its left operand into a new result and then works in place on it. That is the standard way to write them, and it means every operator in an expression makes a new matrix. This runs in Nim 2 and counts the copies:

var copies = 0
type Matrix = object
  a: array[4, array[4, float]]
proc `=copy`(d: var Matrix; s: Matrix) =
  inc copies
  d.a = s.a

proc `*=`(x: var Matrix; y: Matrix) =
  for i in 0..3:
    for j in 0..3: x.a[i][j] *= y.a[i][j]
proc `+=`(x: var Matrix; y: Matrix) =
  for i in 0..3:
    for j in 0..3: x.a[i][j] += y.a[i][j]
proc `-=`(x: var Matrix; y: Matrix) =
  for i in 0..3:
    for j in 0..3: x.a[i][j] -= y.a[i][j]

proc `*`(x, y: Matrix): Matrix = (result = x; result *= y)
proc `+`(x, y: Matrix): Matrix = (result = x; result += y)
proc `-`(x, y: Matrix): Matrix = (result = x; result -= y)

proc main =
  var a, b, c, d: Matrix
  copies = 0
  let e1 = a*b + c - d                  # what you write
  echo "a*b + c - d:        ", copies, " copies"
  copies = 0
  var e2 = a                            # what avoidtemps turns it into
  e2 *= b
  e2 += c
  e2 -= d
  echo "rewritten in place: ", copies, " copy"
  doAssert e1 == e2
main()
a*b + c - d:        3 copies
rewritten in place: 1 copy

Three matrices are made and two of them die at once: they are temporaries. With 16 floats that is a small waste; with a big matrix or a vector of a million elements it is the cost that dominates. C++ solves this with "expression templates", a famous piece of template trickery. Nim 2 had term rewriting macros, a pattern-matching feature that few people used and that was hard to keep working.

In Nimony you attach the rewrite to the type:

type
  Matrix {.plugin: "std/deps/avoidtemps".} = object
    a: array[4, array[4, float]]
avoidtempsexpression templates, term rewriting macros

A type plugin that ships in Nimony's standard library (lib/std/deps/avoidtemps.nim, 302 lines). For every module that uses the marked type, it rewrites chains of + - * / in let/var declarations into one copy followed by in-place operators. A right operand that is itself a chain gets a single temporary: let e = a - (b*c + d) becomes var e = a; var t = b; t *= c; t += d; e -= t. An assignment x = y*z to a local x becomes x = y; x *= z when the right side does not mention x.

Attaching it is a promise by the type's author that x op y means (var t = x; t op= y; t): the plugin cannot see the operators (they live in another module), so it trusts the promise. It leaves globals and var parameters alone, because a parameter on the right side could alias them. std/vectors (the new Vec[N, T] type, merged the same day) is its first user.

Outlined in Araq's design post (3 May 2025) and the manual (Aug 2025); real on 22 Nov 2026 (PR #3089)

Behind that one line sit most of the ideas this page explains: plugins instead of macros, plugins that are ordinary Nim programs compiled to machine code, and a compiler that speaks NIF between every step so a plugin can read and write the program. Here is how all of that came to be.

NIR

"Nim Intermediate Representation", announced in Nov 2023 inside the old compiler: a typed, C-like format for backends only, with a planned new VM, REPL and C++ backend. It was abandoned; NIF took over its job and much more.

Nov 2023
IC

Incremental compilation: after an edit, recompile only the modules that are affected, not the whole program. It was the community's top wish in the 2023 survey and the hardest goal of the project. In Nimony it is not even optional: every build has always been incremental.

the 2023 survey
NIFnifspec

"Nim Intermediate Format", described by Araq as "JSON for compilers". It looks like Lisp: (call foo.0 +4 "abc"). What it adds to Lisp, from the spec and the S-expressions post:

  • Two namespaces. The first word of a node is a tag (call, proc, if) and tags never collide with program names, so new constructs need no new keywords.
  • Symbols with identity. foo.2.mymodule is the second foo of module mymodule; foo.0 is local. A definition is written :foo.0, a use foo.0, so "find all uses" is a text search.
  • Line information on every node, stored as small offsets from the parent node.
  • An index at the end of the file maps each exported symbol to a byte offset, so a tool can jump to one declaration without parsing the rest: "a text-binary-hybrid sharded database".
  • ( and ) can never appear inside strings or names (they are escaped), so counting ( in your editor counts the nodes.
Jul 2024, its own repo nim-lang/nifspec since Dec 2024
nifler

The first tool of the chain: it parses Nim source into a NIF dialect, with no symbol table, so it is fast and can run on just the files that changed. It reused the old compiler's parser until Sep 2026, when Nimony got its own lexer and parser, generated from a grammar DSL by plugins (which also proved "Nim's grammar is in fact LL(1)"). Nifler can also evaluate nim.cfg and NimScript files, so tools like nimsuggest get the right --path without importing the compiler.

Jul 2024
NIFCnow Leng

"NIF representing C": a dialect close to C (types, procs, gotos), from which C code, and later LLVM and native code, is produced. Renamed Leng in Jun 2026, see below.

Jul 2024
gear2, gear3

gear2 (Jul 2024) mapped the entire semantically checked AST of the Nim 2 compiler to NIF, every node flag and pragma, with separate iface and impl sections. It was the first bridge between old and new. gear3 (Nov 2024) was the first tool that lowered checked code to NIFC; in Jan 2025 it was renamed hexer, and in Oct 2026 hexer became part of Shoggoth.

Jul 2024
Aside

Why a native x86 backend as early as 2024? Araq: "Generating native code directly is simpler and more rewarding than generating LLVM's IR", plus a long-term plan to run the generated machine code at compile time instead of keeping Nim's VM. That plan came true in 2026 (see Arkham).

Nimony

The name of the new compiler for the language that will become Nim 3, and the umbrella name for all its tools ("nifler and hexer have been developed in lock-step"). The website puts it this way: Nimony is the compiler; Nim 3 is the language revision; a full Nim 3 release is Nimony "plus substantial compatibility work" so that Nim 2 code can migrate. It is not a drop-in replacement for Nim 2: "Once that happens it will be renamed to Nim 3."

Nov 2024
type-checked generics and concepts

Nim 2 checks a generic proc only when it is instantiated with a concrete type. Nimony also checks it where it is declared. For that it must know what T can do, and a concept says it: proc fib[T: Fibable](a: T): T with Fibable = concept listing <=, + and -. Without the concept, fib is rejected. The payoff: earlier errors and precise IDE completion. A generic marked .untyped keeps the old behaviour. "Every toy example I throw at Nimony requires a concept declaration. I think we're really getting into shape here."

Feb 2025
.view and library openArray

In Nim 2, openArray[T] is a special built-in type. In Nimony it is an ordinary object (a pointer and a length) whose declaration carries the .view pragma, which tells the compiler to apply borrow rules to it. Fewer special cases in the compiler, and user-defined view types work the same way.

Mar 2025
polymorphic accessors

Nim 2 needs two overloads, [](x: var C): var T and [](x: C): lent T. Nimony needs one, [](x: C): var T, and tracks whether a write through it is allowed (it is when x is mutable), as built-in arrays always did. A bonus: a container access that could resize the container still needs var, so the type system knows which accesses are safe. (Overloading on var T came back in May 2026 "for backwards compat".)

Mar 2025, explained Aug 2025
contracts: .requires, .ensures, .assume, .assert

.requires states what a call needs (i >= 0 and i < s.len for indexing), .ensures what a routine guarantees. The compiler tries to prove each call site: proven costs nothing, violated is a compile-time error, undecided keeps a run-time check. .assume and .assert are escape hatches. Since seq indexing is itself a .requires, this is how bounds checks disappear. See the manual.

aufbruch mode

Mar 2025
pluginscompiler plugins

"Plugins are the final evolved form of Nim's macros." A plugin is a Nim program, compiled to a native executable, that reads the code to transform from an .in.nif file and writes the result to an .out.nif file. Compared with Nim 2's macros, which run in the compiler's VM: every language feature works (including unsafe code), they see fully type-checked input, they run incrementally and in parallel, and the implementation is about 100 lines instead of a VM. Four kinds, from the plugins doc:

  • template plugins: template foo(x: int) {.plugin: "foo".}, the macro replacement;
  • module plugins: {.plugin: "cps".} as a statement receives the whole module;
  • type plugins: attached to a type, run for every module that uses it (avoidtemps);
  • import plugins: import foo {.plugin: "v2".} imports a module that a plugin produces, even from another language.

Macros came back in May 2026, mapped onto plugins, "so that you can keep your macros for good", but plugins are "definitely the recommended approach".

first one ran 22 Apr 2025
ErrorCode and .raises

A routine that can raise must say {.raises.} (without listing what: the point is that the call hides control flow). Besides exceptions you can raise ErrorCode.RangeError, a plain enum designed to map to POSIX errno, Windows errors and HTTP status codes. No heap allocation is needed to raise, so even out-of-memory can be propagated. Heap-based exceptions (ref object subtypes) were added later for compatibility (Feb 2026). See the design post.

Apr 2025
OOM handling

Araq's view: "OOM is a misnomer", one request of one size failed. Containers that cannot allocate call an overridable oomHandler and stay in an empty state; new returns nil, and because nil is checked at compile time you must handle it. Inside a .raises proc new instead never returns nil: the failure becomes ErrorCode.OutOfMemError.

design post, May 2025
nil ref T and not-nil by defaultlenientnils

Three kinds of pointer were discussed for weeks (with dozens of syntax proposals): unchecked, nil ref T (may be nil, every dereference must be guarded), and not-nil. The result, default since Apr 2026: a plain ref T or ptr T cannot hold nil; write nil Node for one that can. The compiler follows if x != nil through control flow. A not-nil pointer has no default value, so var a: array[8, Node] does not compile. Old code can opt out per module with {.feature: "lenientnils".} (doc).

nifmake

A make-like engine over a dependency graph written in NIF. The driver writes the graph (which module needs which), nifmake runs every tool whose inputs are newer than its outputs, as many at once as there are cores. The trick that spares work: each module also writes a small interface file (M.s.idx.nif), rewritten only when what other modules read from it changed, so editing the body of a non-generic proc recompiles nobody else. See the IC rules.

Jun 2025
v2 import plugin

An import plugin that shells out to the Nim 2 compiler (nim nif) to translate a Nim 2 module into Nimony's NIF, including the index. It is the bridge for libraries not yet ported, and it takes part in incremental builds.

Jun 2025
lambda lifting

The classic compiler step that turns a nested proc capturing local variables into a top-level proc plus an explicit environment object. Nimony also checks whether the environment can live on the stack (the closure does not escape), which avoids the heap allocation entirely.

Jun 2025
CPS

Continuation-passing style. The compiler cuts a routine at the points where it may pause and turns each piece into a small function that returns "what to run next" (a continuation: a function pointer plus an environment). The local variables move into a heap object. A loop (the trampoline) keeps calling "what to run next" until nothing is left. Tail calls and closure iterators come out of it for free. Nim 2 has CPS as a library (nim-works/cps); in Nimony it is a compiler pass.

planned Feb 2025
passive procsasync, coroutines

Nimony's answer to async/await: mark a proc {.passive.} and write no await at all. "It's passive, it needs to be stepped through by a scheduler." Calling a passive proc from another passive proc is a suspension point; calling it from normal code runs it to completion, so it looks like a blocking call. The pieces, from passive_procs.md:

  • Continuation: a function pointer plus an environment; fn == nil means finished;
  • delay(call): make a continuation without running it, to hand to a scheduler (its parameters must not alias the caller's frame, take them as sink);
  • suspend() / delay(): park the current task, to be resumed when I/O is ready;
  • complete(c): run a continuation to completion from ordinary code;
  • the scheduler is replaceable, so a thread pool and an event loop are the same mechanism: "Async event loop unified with multi-threading."

A user report: tokyovigilante's CPS web server Hashi reached parity with Mummy.

Aug 2025
compile-time evaluation by compiling

Nim 2 runs compile-time code (const, macros) in a VM with many restrictions. Nimony does not have a VM: it compiles the snippet through the full pipeline to a native executable, runs it, and reads the result back, like plugins. "Restrictions on compile time execution? Yes, these are all gone." See design.md.

Sep 2025
NJVLNJ, cfvars, versioned locations

An intermediate representation with no jumps: return, break and goto become boolean control flow variables ("cfvars", set once and never reset), and versioned locations: every write to a variable gets a version number, like SSA but for any location and without SSA's phi nodes (the merge points that are "subtle to understand and to get rid of"). The promise: inlining, move analysis, destructor injection, CSE and nil checking all become simple tree walks. Follow-ups: a bind construct to merge CSE, copy propagation and scalar replacement (Oct 2025), and "SSU" (static single use, Nov 2025).

It shaped the project for a year: in Jan 2026 it became NJ, the planned common backend for Nim 2 and Nimony; in Mar 2026 the proof engine was moved onto it. Then the repo moved to the multi-join IR instead, and on 31 Aug 2026 the commit "njvl: remove the superseded pipeline" deleted it. The repo's instructions for AI agents now say: "NJVL is dead. Do not resurrect it."

21 Oct 2025
phi nodes and SSA

SSA (static single assignment) is the form most optimizing compilers use: every variable is assigned exactly once, so x = 1; x = 2 becomes x1 = 1; x2 = 2. Where two branches meet, a phi node says "x3 is x1 or x2, depending on where we came from". Phi nodes are what NJVL's versioned locations replaced with fixed join points in the tree.

token streams and cursorsPackedToken, TokenBuf, Cursor

The design Araq is proudest of (Implementing NIF). Nimony never builds a tree of node objects. A module is a flat buffer (TokenBuf) of PackedTokens, 8 bytes each: 4 bits of kind, 28 bits of payload (an id into a string, symbol or number table), and 4 bytes of packed line information. A "tree" is just (, children, ) in that array, and a cursor walks it, skipping a subtree by counting parentheses. Each pass reads one buffer and writes a new one.

Why it is safer: the closing ) tokens are explicit, so a pass that forgets to handle a child breaks the parenthesis count at once, where a tree-based pass would silently drop n.left. A buffer is sealed while a cursor reads it (no iterator invalidation) and cannot be copied (a Nim 2 =copy hook marked .error). "The tree exists only implicitly in the call stack." Helper structures like symbol tables are built for one pass and thrown away.

cyclic imports

Nim 2 forbids import cycles, which forces people to merge modules or make fields public. Nimony needs no forward declarations, so cycles are possible: every import in the cycle must be marked import foo {.cyclic.}.

Feb 2026
borrow checkinguncheckedBorrow

While you hold a borrow (for example iterating with mitems(data.items)), you may not mutate the borrowed path or any prefix of it (data, data.items), but you may read it and you may mutate disjoint siblings (data.metadata). Borrowing is only allowed from simple paths (data.items[i], not getPtr()[].field), so the compiler can check it locally. Paths through a ref are rejected because another alias could change them: either move the container out and back in, or write uncheckedBorrow app.users to take the responsibility yourself. Araq's rules, posted in Oct 2026; the rules were also modelled in Lean (a proof assistant), which found bugs. "The borrow checker is now considered to be complete" (20 Oct 2026). Nim 2 will get it next.

Apr 2026
strings: SSO, COW, no terminating zero

Nimony strings dropped C's terminating zero (it costs memory and rules out O(1) slicing), so converting to cstring is explicit and may copy. Since Mar 2026 they use small-string optimization (short strings live inside the string header, no allocation) and copy-on-write (copies share the buffer until one is changed).

LengNIFC, Arkham IR, lengc

The dialect that used to be NIFC, renamed in Jun 2026 to end the NIF/NIFC confusion. It is C's level of abstraction written as NIF: types, procs, structured control flow, no generics or closures. Every backend reads it: lengc turns it into C (or LLVM text), arkham into machine code, the JS and wasm backends into theirs. Also called the Arkham IR. Spec.

Shoggothhexer, Shoggoth IR

Named after the Lovecraftian monster. It first appeared in Jun 2026 as the optimizer working on Leng (inlining across modules, CSE, a vectorizer, run for --opt:speed/size). On 6 Oct 2026 hexer was folded into it: "Hexer is gone and part of Shoggoth. This one was very important to me personally as Hexer is no lovecraftian monster." Arkham and nifasmNativeNif, nimony n

arkham (Arkham is Lovecraft's fictional town) turns Leng into machine code for x86-64 and arm64 (Cortex-M and RISC-V 32 partly), and nifasm, a typed assembler, assembles and links it into ELF, Mach-O or PE executables: no C compiler, assembler or system linker. assembler procs

An {.assembler.} proc is machine code in Nim syntax: each statement is one instruction, every local declares its register (var t {.register: "r8".}: uint64), and nothing is reordered. Its use: code whose correctness depends on which instructions run, above all constant-time cryptography (std/crypto/x25519, chacha20poly1305). The httpclient with its own TLS (Oct 2026) was built to try out this "Nim-as-inline-assembler design". Doc.

BIF

"Binary NIF": the token stream written as raw 32-bit tokens with an index, little-endian, with a version byte (now 5). It trades readability for loading speed (memory-mapped, no parsing). Converters nif2bif/bif2nif exist. Third parties wrote codecs (nifkit).

nifcore

The third generation of the library that reads and writes NIF inside the toolchain, with lower memory use, binary BIF support and a plugin API on top. The whole codebase was ported to it by Jul 2026; plugins too.

multi-join IR (Final IR)Final IR

What replaced NJVL in practice. Control flow is reduced to three things: loop (one back edge, no condition slot), ite (if-then-else), and forward, scoped (jmp L) to a (lab L); any number of jumps may join at one label, hence the name. Control flow inside expressions is lowered to statements, so any sub-expression can be hoisted into a statement just before its own (the "hoisting rule" every later pass relies on). The front end lowers to it as its last step and runs the prover on it, so the published module already says which run-time checks are still needed. The code still calls it "Final IR". Doc.

{.feature: "staticContracts".} turns "undecided" into an error for every contract in the module, so all array indexing is proven in bounds at compile time: "making IndexError exceptions a thing of the past". strutils compiles with it since 28 Oct 2026; since 4 Nov the prover also reasons about integer overflow. dwhall256's thread walks through the strutils diff.

|| parallel for

for i in 0 || 1: r[i] = pfib(n - 1 - i): like 0 .. 1, but every iteration runs in parallel. The compiler checks that the writes r[i] do not race, and the parallelism ends with the loop. No spawn, no FlowVar, no sync. Araq considers it simpler than his Malebolgia library.

memory management modesARC, ORC, YRC

Nim 2's destructor-based memory management, reimplemented ("Nim 2's way of doing it is basically perfect"). Values are freed when their owner goes out of scope; refs are reference counted. --mm:atomicArc (default) updates counts atomically so refs can cross threads; arc without atomics; orc adds a cycle collector; yrc is a thread-safe orc whose collector runs concurrently. A strategy is just a file lib/std/system/<name>.nim defining three primitives, so --mm:<path> plugs in your own. stdlib guide.

Oct 2026
owned ref T

owned X marks the location that holds the unique owning edge to a ref cell; ordinary refs to it can still exist and keep it alive. Copying an owned location is an error (move it instead), and {.feature: "ownedRefs".} makes object construction return owned. It gives a way to build parent/child structures without cycles. Manual.

strict funcs

Nim 2's --experimental:strictFuncs: a func may not change anything reachable through its parameters' refs, not only its own variables. In Nimony func, iterator and converter are side-effect free by default and proc is not. Turning strict funcs on broke no stdlib code.

term("token streams and cursors", "no AST: the program is a flat array of 8-byte tokens", &"""
The design Araq is proudest of ([Implementing NIF]({blog}nif_implementation.html)). Nimony never
builds a tree of node objects. A module is a flat buffer (`TokenBuf`) of `PackedToken`s, 8 bytes
each: 4 bits of kind, 28 bits of payload (an id into a string, symbol or number table), and 4
bytes of packed line information. A "tree" is just `(`, children, `)` in that array, and a
**cursor** walks it, skipping a subtree by counting parentheses. Each pass reads one buffer and
writes a new one.

Why it is safer: the closing `)` tokens are explicit, so a pass that forgets to handle a child
breaks the parenthesis count at once, where a tree-based pass would silently drop `n.left`. A
buffer is sealed while a cursor reads it (no iterator invalidation) and cannot be copied (a
Nim 2 `=copy` hook marked `.error`). "The tree exists only implicitly in the call stack."
Helper structures like symbol tables are built for one pass and thrown away.
""", taka = "PackedToken, TokenBuf, Cursor", tsince = "the design since 2024; [explained Mar 2026](" & blog & "nif_implementation.html)")
